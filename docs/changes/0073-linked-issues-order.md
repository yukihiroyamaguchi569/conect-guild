# #73 PR の linkedIssues: Issue の一覧を PR の一覧より後に取り、取得の間に作られた Issue を落とさない（2026-10-12）

- PR #69（#68）のレビューで出た 2 点のフォローアップ
- collector は Issue の一覧と PR の一覧を並行に取っていた。#68 で `linkedIssues` を実在する Issue だけにしたので、Issue の一覧を読んだ直後に作られた Issue を PR が参照していると、その周期だけ結び付けが落ちていた（60 秒後の次の周期で戻るが、`collect:once` ではそのまま残る）。PR の一覧を取り終えてから Issue の一覧を取る順にした。PR を読んだ時点で既にある Issue は、後から取る Issue の一覧に必ず入る。Issue を後から取り直す案より単純で、API の回数も変わらない。1 回の取得は、2 つの一覧の短いほうを読む時間（いまの件数で数秒）だけ長くなる。起動直後の最初の 1 回の待ちもその分伸びる
- 0068 の「画面の結果は変わらない想定」は正確でなかった。`Closes #999`（実在しない）と題名の `#7`（実在する）がある PR は、#68 の前は `#999` だけに結ばれ（snapshot に無いので担当はブランチ名で決まる）、#68 の後は `#7` に結ばれるので、担当が `#7` の部門に変わりうる。GitHub のリンクの扱いに合わせた結果なので、この挙動のままにする。collector の結び付けから画面の担当の判定（assignPr）まで通すテストを足した
- 関係する章: 4.1 の「API の呼び出し回数」と「PR と Issue の結び付け」、4.5
