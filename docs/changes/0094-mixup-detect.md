# #94 collector: 部門の設定の取り違え（ラベルとフォルダ・接頭辞の入れ替わり）を疑ったら知らせる（2026-10-13）

- #79 の検討で、形は正しいが中身が違う取り違え（広報と企画の接頭辞が入れ替わっているなど）は入口がどれでも起こりうると社長が指摘した。書く前の備え（#99）とは別に、動きだしてから気づく仕組みとして #94 を起こし、#79 の土台のあとに着手した（社長の指示）。次のようにした（DESIGN.md 3 章・4.1・4.3）
- 判断の基準（社長の判断、2026-10-13。Issue #94 のコメントに記録）
  - 直近 30 日の PR のうち、部門 i の接頭辞の PR で、結び付いた Issue が部門ラベルを 1 つだけ持つものを数える。別の 1 部門 j のラベルのものが 3 件以上、かつ部門 i の数える PR の過半数（ちょうど半分は疑わない）なら疑う
  - 部門ラベルが 2 つ以上の Issue、部門ラベルが無い Issue、Issue に結び付いていない PR は数えない
  - 知らせ方は #85 と同じ帯とログ。両方向がそろえば「入れ替わっているかもしれません」、片方向だけならその向きを出す。ログには添字と件数だけを出し、ラベル名・題名・ブランチ名は出さない
  - 判定は純粋関数にし、#79 の土台からも使える場所に置く
- 実装時の判断
  - 判定 `suspectedMixups` と組み分け `mixupFindings` は `packages/snapshot/src/mixup.ts` に置いた。collector と画面の両方が使い、collector の内部の状態に頼らない。部門の数は引数で受け、4 つに限らない
  - 30 日はマージの日時（`merged_at`）で測る。collector が PR から取っている日時は `merged_at` と `closed_at` だけで、取得を増やさずに済む。マージ済みの PR は結び付きが確定した成果物で、経験値の履歴（`history.mergedPrs`）と同じ範囲になる。open の PR と、マージせずに閉じた PR は数えない。読むものは CLAUDE.md の「会話の中身に触れない」の範囲（番号・ラベル・状態・日時・ブランチ名と、`#番号` を拾うための題名・本文）のまま
  - 1 つの PR が複数の Issue に結び付くときは、部門ラベルがちょうど 1 つの Issue だけを見て、それらがすべて同じ部門を指すときに 1 件と数える。別々の部門を指せば部門をまたぐ仕事として数えない
  - 状態ファイルには添字の組 `suspectedMixups: [{ from, to }]` だけを書き、件数は入れない（帯に要らないため）。疑いが無いときは項目ごと書かない。GitHub の取得に失敗したら前の結果を残す
  - ログは結果が変わったときだけ出す。起動して何も疑わないときは何も出さず（毎回の起動のログを増やさない）、疑いが消えたら `mixups ok` を 1 回出す
  - 帯は 1 本だけにし、ラベルの食い違い（#85）があればそちらを先に出す。両方を重ねると画面の高さの計算（`--banner-height`）を変える必要があり、ラベルを直せば取り違えの帯が出るので足りると考えた
  - 直し方は docs/setup.md の 3 章に「画面の帯に『部門の設定が入れ替わっているかもしれません』と出る」の節を足した。確かめるのは `branchPrefixes` の `department` と、部門のフォルダの `CLAUDE.md` が指示するラベルと接頭辞。`sessionDir` だけが入れ替わっても、セッションが作るブランチと Issue のラベルの組は変わらないので、この判定には出ない
