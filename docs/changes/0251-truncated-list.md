# #251 collector: GitHub の一覧が途中で切れた回の snapshot でレベルアップが重なる（2026-10-22）

- `gh api --paginate` の Issue の一覧（PR を含む）が、途中のページを短く返して終了コード 0 で終わることがある（実測で全体 6 ページのところ `100,100,100,39` の 4 ページで終わった回と、5 ページで終わった回があった）。collector がその一覧で snapshot を書くと履歴の件数が一時的に減り、画面でレベルが下がって上がり直し、同じ LEVEL UP が重なって出ていた。PR の一覧も同じことが起こりうる
- 一覧を取る前に `gh api graphql` で Issue（PR を除く）と PR の総数（`totalCount`）だけを取り、一覧で数えた件数と比べる。owner と name は `-f` の変数で渡し、クエリの文字列に埋め込まない（`-F` は `123` のような名前を数に変えるので `-f` にした。実装時の判断）。応答は件数 2 つだけの形を zod で検証する（社長の判断）
- 一覧が総数より少なければ取得の失敗（`validation-failed`）として扱い、snapshot を書き換えない。新しいエラーの種類は足さなかった。種類は画面の帯の文言と結び付いており、画面は変えないため（実装時の判断）
- 比べ方は「重複を除いた番号の数 < 総数で失敗」にし、総数を一覧より先に取る。途中で切れた一覧は少なくなる方向にしか外れず、読んでいる間に作られた Issue・PR は多くなる方向にしか外れないので、作成では失敗にならない。ページのずれで同じ番号を 2 回読むことがあるので、重複を除いて数える（2 回読んだ分で欠けた分が隠れないように）。読んでいる間に削除・移動されたときはその回だけ失敗し、次の回で取り直す（実装時の判断）
- 実装の前に 2026-10-22 に `yukihiroyamaguchi569/conect-management` で件数だけを確かめ、ふだんの回では一致した（Issue 171 件、PR 400 件）
- お客さん（guestGithub.ts）は 1 ページだけを取り、`--paginate` を使わないので変えていない
- 1 回の GitHub の取得で `gh` の呼び出しが 1 回増える。関係する章: 4.1 の「Issue」「PR」の次の「一覧の件数の確かめ」
