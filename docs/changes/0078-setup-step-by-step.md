# #78 docs/setup.md をステップバイステップで分かりやすく書き直す（2026-10-12）

- docs/setup.md を「0 使える条件 → 1 まずデモを見る → 2 自分のリポジトリで使う → 3 困ったとき → 4 MulmoTerminal との関係・絵の差し替え・データの扱い」の順に書き直した。#71・#72・#74・#76 の継ぎ足しで、条件が手順の途中に埋もれていたため（社長の要望）。2 章は各ステップを「やること → 確かめること」の形にし、`npm run dev:all` のログ（`settings:`・`ok:`・`sessions=`）の見方を足した。3 章は帯・ログの失敗の種類ごと、設定の検証のメッセージごとに直し方を表にした。4 章は今の内容（とくにデータの扱い）を残した
- docs/orchestration.md を新しく作った。conect-guild はエージェントが決まった流儀で GitHub を使うことを前提に絵を描くので、その流儀（役割、Issue → 部門ラベル → ブランチ → PR → マージ、マージの分担、承認の扱い）、始め方（人が書くのは司令塔の CLAUDE.md だけで、部門のフォルダ・CLAUDE.md・ラベルは司令塔に作らせ、部門の CLAUDE.md は PR で社長の承認を待つ。セッションの起動は社長が MulmoTerminal で行う）、司令塔の CLAUDE.md の雛形、部門の CLAUDE.md の例、社長の決定の記録と回収、社長のプロンプトの例を載せた（社長の判断、Issue #78 の追記 3 件と、その後の判断）
- 社内の CLAUDE.md は写さず、流儀の部分だけを汎用の雛形として書き起こした。例の依頼・題名は架空のもの
- 社長の決定待ちの点は控えめに書いた: ブランチ名（`<フォルダ>/<番号>-<英語>`）と `Closes #番号` は「conect-guild がうまく描けるおすすめの書き方（提案）」とし、雛形の中でも決まりとは書かない。`Closes` でマージと同時に Issue が閉じるので、司令塔の確認はマージの前にする流れにした（レビューの指摘）。司令塔の名前の例として「かなめ」を残す。外部の AI にレビューさせる運用と、社内の失敗の経緯は載せない。決定を Issue のコメントから回収する `gh` のコマンドは、載せてよいという社長の判断により、リポジトリ名を `<owner/name>` にし、運用開始の日時による絞り込みを外した形で載せた
- README（日・英）の「できること」の下に、部門は 4 つで固定であることと setup.md の「使える条件」へのリンクを足し、「もっと知る」に orchestration.md を足した（英語版は「(Japanese)」を添える。英語版の orchestration.md は作らない）
