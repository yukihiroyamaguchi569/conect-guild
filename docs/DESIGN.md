## 1. 何を作るか

conect.llc の「AI だけで動く会社」（司令塔かなめ 1 + 部門セッション 4 + 社長）を、レトロ RPG のギルド画面として眺めるアプリ。目標の見た目は codex に描かせたコンセプト画（`assets/concept/rpg-company-ui.png`）。

見立て:

| 会社 | ゲーム |
|---|---|
| GitHub Issue（部門ラベル付き） | クエスト（掲示板の巻物） |
| 部門セッション（経理・広報・企画・総務） | パーティのメンバー |
| かなめ（司令塔） | ギルドの受付。巻物を担当の机まで運んで手渡し（近い机にはときどき受付から投げて渡す）、担当の宝箱を受付で受け取って掲げる（部屋から出る演出はしない） |
| 社長 | 玉座の王。承認待ちは「承認まち」の吹き出し |
| PR | 宝箱（成果物）。マージで担当が受付のかなめに届け、「最近の成果」に加わる |
| Issue のクローズ | 「クエストをクリアした！」のメッセージ |

作らないもの（v0.2 の範囲外）: 会話の中身の表示、セッションへの操作（指示を送るなど）、公開ホスティング、ビルド成果物（`dist/`）の配布。

### メンバーの名前

部門にはかなめと同じように名前を付ける（社長のリクエスト、2026-10-12）。名前はリポジトリ直下の設定ファイル（`guild.settings.local.json`、無ければ `guild.settings.json`。3 章、10 章 9）に置き、後から変えられるようにする。社長が確定した名前（2026-10-12）:

| 部門 | 名前 | 由来 |
|---|---|---|
| 司令塔 | かなめ | 扇の要 |
| 経理 | みのり | 実り。お金と成果を数える |
| 広報 | ひびき | 響き。声を外に届ける |
| 企画 | ひらめ | 閃き。案を生む |
| 総務 | ささえ | 支え。会社を下から支える |
| 社長 | ゆきひろ | 王様 |

GitHub 上の部門ラベル（`経理` など）とは対応表で結び、Issue やコメントの書式は変えない。

## 2. 設計の原則

1. **TypeScript だけ。** フロントも収集スクリプトも TS。`any` と unsafe cast は使わない（`~/.claude/rules/code-quality.md`）
2. **依存は最小限。** 本体の実行時依存は Vue と zod（外部入力の検証。型は schema から推論する）の 2 つだけ。Canvas はブラウザ標準の機能なので追加なし。PixiJS などの描画ライブラリは入れない
3. **ブラウザから外部へ通信しない。** GitHub API はブラウザから呼ばず、ローカルの収集スクリプトが `gh` CLI で取って JSON に落とす。ブラウザはその JSON を読むだけ。トークンをフロントに置かない（`gh` の認証をそのまま使う）
4. **待ち受けを増やさない。** 立てるサーバーは Vite の開発サーバーだけで、`127.0.0.1` に固定する（`vite.config.ts` の `server.host` と、設定ファイルを読めなかったときのために `apps/web` の dev スクリプトの `--host 127.0.0.1`。それ以外の `--host` は使わない）。独自の HTTP/WS サーバーは作らない。安全性調査（2026-10-12）で pixtuoid がいちばん安全だった理由と同じ
5. **会話の中身に触れない。** 読むのは Issue・PR の番号・題名・ラベル・状態・日時・ブランチ名と、open PR の変更ファイルのパスだけ。PR の題名と本文は対応 Issue の番号を拾うためだけに読み、本文は保存しない。セッションの状態（M3）は hooks を足さず、MulmoTerminal が書くファイルから会社の 5 セッションの行だけを読み、部門と状態（作業中・許可待ちなど）だけを残す。会話・ツールの入力・会社以外のセッションのパスや ID は読まず、保存もログもしない（4.7）
6. **ロジックは純粋関数に。** Issue → クエスト、状態の導出、最近の成果の計算は副作用のない関数にして vitest で守る。UI（Vue / Canvas）には判定を書かない
7. **実データは配信物に入れない。** Issue の題名には取引先の名前が入るので、画面は手元で見るもの。実データは `apps/web/public/` に置かず、ビルドにも入れない（5 章の「公開範囲」）。GitHub Pages などに載せない
8. **外部の文字列は文字として描く。** Issue・PR の題名やラベルは外部入力なので、Vue のテキスト補間（`{{ }}`）か Canvas の `fillText` だけで描く。`v-html`、`innerHTML` などの HTML への直接挿入、外部 URL の画像・フォント・スクリプトの読み込みは使わない（画面にスクリプトを差し込まれると、手元の snapshot を外へ送られる）

## 4. データの流れ

```
GitHub（設定ファイルに固定したリポジトリの Issue / PR）    MulmoTerminal のファイル（~/.mulmoterminal/、読むだけ）
   │  gh api（execFile で引数配列。gh の認証を使う。60 秒ごと）          │  会社の 5 セッションの行だけ（5 秒ごと、4.7）
   ▼                                                                      ▼
packages/collector ──検証して一時ファイルに書き rename──▶ apps/web/.data/snapshot.json（0600、gitignore）
                                                              │  開発時だけ: Vite の自作プラグインが
                                                              │  GET /snapshot.json に Cache-Control: no-store で返す
                                                              ▼
                              画面: 5 秒ごとに fetch('/snapshot.json', { cache: 'no-store' })
                                                              ▼
                              domain: zod で検証 → Quest / Party / Reward / Events
                                                              ▼
                              ui（Vue） + render（Canvas、M2〜）
```

### 4.1 収集（packages/collector）

- **対象リポジトリ**: 設定ファイルの `repo` に固定する（既定 `yukihiroyamaguchi569/conect-management`）。設定ファイルは、リポジトリ直下に手元だけの `guild.settings.local.json` があればそれ、無ければ `guild.settings.json`（10 章 9。Issue #76）。コマンドライン引数や環境変数では変えられず、どちらを読むかもファイルの有無だけで決まる。設定ファイルを書き換えて変える
- **起動時のログ**: 読んだ設定ファイルの名前だけを 1 行出す（`[collector] settings: guild.settings.local.json`）。中身は出さない
- **`gh` の呼び方**: `child_process.execFile('gh', [引数の配列])`。シェル文字列は組まない。認証はユーザーの `gh` のものをそのまま使う
- **ページ送り**: `gh api --paginate --jq '<射影> | @json'` で、要るフィールドだけに絞った要素を 1 行 1 JSON で受け、行ごとに zod で検証する（`--slurp` は `--jq` と併用できない）。差分の中身や Issue の本文は gh の段階で落とす。ページが配列でなければ jq でエラーにし、空の一覧と取り違えない。`execFile` の `maxBuffer` は 64 MB にし、超えたら失敗として扱う。テストは複数ページの出力で行う
- **Issue**: open と closed を 1 つの一覧（`state=all`、作成日の新しい順）で全ページ取る。closed を `since` で絞らない（累積の経験値の履歴を毎回数え直すため。Issue #19）。open と closed を別々に取ると、その間に閉じた・開き直した Issue が両方から漏れうるため、1 つの一覧にした。作成日の順なので、読んでいる途中で状態が変わってもページの位置は動かず、どちらかの状態で 1 回は読める。途中で新しい Issue が作られるとページがずれて同じ Issue を 2 回読むことがあり、そのときは後で読んだ方（新しい方）を使う。snapshot の `issues` には open の全部と、直近 7 日に閉じたもの（`closed_at` で確かめる）を同じ一覧から入れる。閉じた理由（`state_reason`）も受ける。GitHub が後で理由の種類を足しても止まらないよう、文字列か null として検証する。GitHub の Issue 一覧には PR が混ざるので、`pull_request` キーを持つものは除く
- **PR**: open と closed を 1 つの一覧（`state=all`、作成日の新しい順）で全ページ取る（pulls の API に `since` は無い）。以前の closed の一覧は更新日の新しい順で、読んでいる途中で古い PR が更新されると先頭へ移り、どのページでも読めないことがあった。作成日の順なら位置は動かない。snapshot の `prs` には open の全部と、直近 7 日に閉じた・マージされたものを同じ一覧から入れる。変更ファイルを取るのも、この一覧で open だった PR だけ
- **履歴（`history`、Issue #19）**: 取った全履歴から毎回数え直す。差分で足し込まないので、取りこぼし・再オープン・ラベルの付け替えは次の取得でそのまま正しくなる。入れるのは番号と部門だけ（4.2）
  - 開かれた Issue の総数（`openedIssueCount`）: open と closed の Issue の件数（PR を除く）。閉じた理由を問わない。かなめの「受付で配った巻物」（4.6）は、Issue が開かれた時点で受付が配ったものなので、あとで「Close as not planned」や重複で閉じたものも含める
  - completed で閉じた Issue（`completedIssues`）: `state_reason` が `completed` のものだけ。部門ラベルだけを固定の順で残す。not planned・duplicate・理由なし・再オープン中のものは入れない
  - マージ済みの PR（`mergedPrs`）: `merged_at` があるものだけ。リンクした Issue の番号（上の結び付けと同じ規則）と、ブランチ名を `branchPrefixes` に当てて引いた部門（当たらなければ null）。ブランチ名そのものは collector の中で部門に変えて捨て、履歴には入れない
  - Issue も PR も、ページのずれで同じものを 2 回読んだら後で読んだ方（新しい方）を使う。番号の順に並べる
- **API の呼び出し回数**（2026-10-12 に件数だけを確かめた: closed の Issue 109 件、closed の PR 198 件、open の Issue 2 件、open の PR 0 件）: 1 回の GitHub の取得で、Issue の一覧（PR も混ざるので 2 + 109 + 198 = 309 件）4 回、PR の一覧（198 件）2 回、open PR ごとの変更ファイル 1 回ずつ（100 ファイルまで。それを超える PR は 100 ファイルごとに 1 回）。Issue #19 の前は open の Issue 1 回、直近 7 日の closed の Issue 1 回、open の PR 1 回、closed の PR 2 回の計 5 回だったので、増えるのは 1 回/分（約 60 回/時）。全体で約 6 回/分（約 360 回/時、open PR が無いとき）で、`gh` の上限 5000 回/時の 1 割に収まる。Issue が 100 件増えるごとに 1 回/分、PR が 100 件増えるごとに 2 回/分（Issue の一覧と PR の一覧の両方）増える。Issue と PR が合わせて 2000 件を超えたら（Issue の一覧だけで 20 回/分）、履歴の取得だけを 10 分ごとに間引くことを考える。そのときも数え直しの考え方は変えない。PR の一覧と Issue の一覧は並行に取らず、PR の一覧を取り終えてから Issue の一覧を取る（下の「PR と Issue の結び付け」。Issue #73）。回数は変わらないが、1 回の取得は長くなる（並行なら 2 つの一覧の長いほうの時間で済んでいたのが、両方の和になる。増えるのは短いほうの一覧を読む時間で、いまの件数で数秒）。GitHub の取得は裏で走るので、ふだんはセッションの 5 秒の周期を止めない。起動直後の最初の 1 回は取得の完了を待つので（下の「間隔」）、その待ちがこの分だけ伸びる
- **PR と Issue の結び付け**: PR の題名と本文から、同じリポジトリを指す参照（`#番号` と `<対象リポジトリ>#番号`）を正規表現で拾い、`linkedIssues: number[]` として持つ。別リポジトリの参照（`owner/other#番号`）は拾わない。対象リポジトリに実在する Issue の番号（取得した全履歴の Issue。PR の番号は含めない）だけを残し、ほかは捨てる（GitHub も実在する Issue だけをリンクにする。本文の例として書かれた `#99999999999999999999` などで snapshot の検証が落ちないように。Issue #68）。`Closes`・`Fixes`・`Resolves` の後の参照が 1 つでもあれば（実在するものに限る）、それだけを使う。このため、`Closes #999`（実在しない）と題名の `#7`（実在する）がある PR は `#7` に結ばれ、担当（4.5）は `#7` の部門になる。Issue の一覧は PR の一覧の後に取る。PR を読んだ時点で既にある Issue は、後から取る Issue の一覧に必ず入るので、2 つの一覧の取得の間に作られた Issue への結び付けが落ちない（Issue #73）。本文そのものは保存しない
- **変更ファイル**: open PR だけ、`gh api --paginate --jq` で `repos/<r>/pulls/<n>/files` の `filename` だけを取り、`changedFiles: string[]` として持つ（差分の中身は取らない）
- **間隔**: GitHub は 60 秒ごと（`gh` のレート制限に十分収まる）。collector 自体は 5 秒ごとに回り、セッションの状態（4.7）を読むたびに、GitHub の最後の正常な結果と合わせて snapshot を書き直す。GitHub の取得は裏で走らせ、遅くてもセッションの 5 秒の周期を止めない（最初の 1 回だけは、書くものが無いので待つ）。周期は予定時刻から数え、1 回の処理の時間も 5 秒に含める。処理が予定を過ぎたら、取り戻そうと続けて回さず、次の予定まで飛ばす。`--once` で 1 回だけ（GitHub とセッションを 1 回ずつ）実行もできる
- **書き込み**: 取得した結果を zod で検証してから、同じディレクトリの一時ファイルに 0600 で書き、`rename` で `apps/web/.data/snapshot.json` を原子的に置き換える。画面が書きかけの JSON を読むことはない
- **失敗したとき**: GitHub の取得や検証に 1 つでも失敗したら、GitHub の部分は直前の正常なもの（`fetchedAt` も直前のまま）を使い、空の配列で上書きしない。起動してから GitHub が一度も成功していなければ snapshot を書かない（その間、開発サーバーは `/snapshot.json` に 204 を返し、画面は自動のデモを流す。4.3）。セッションの状態が読めないときは `sessions` を `unavailable` にし、GitHub の部分の書き込みは妨げない
- **状態ファイル（Issue #74）**: snapshot が無いとき、画面が「collector を動かしていない」と「動いているが失敗している」を見分けられるように、collector は自分の状態を `apps/web/.data/collector-status.json` に書く。中身は最後に GitHub を試した時刻（`attemptedAt`）、成功したか（`ok`）、失敗の種類（`kind`。`gh-failed`・`validation-failed`・`write-failed`・`unexpected` のどれか。ログに出す種類と同じ）だけで、リポジトリ名・題名・本文・パスは入れない。schema は `packages/snapshot` の `collectorStatusSchema`（余分な項目を拒む）。snapshot と同じく一時ファイルに 0600 で書いて `rename` で置き換える。GitHub は成功したが snapshot を書けない間は `write-failed` にする（画面には何も届かないため）。ループでは中身が変わったときだけ書く（GitHub を試すたび（60 秒ごと）と、snapshot の書き込みの失敗が始まった・終わったとき。5 秒ごとには書かない）。同じ周期の snapshot を書いた後に書く。`--once` でも 1 回書く。状態ファイルを書けなければ `status not written: write-failed` を失敗が続く間 1 回だけ出し、次の周期で書き直す（終了コードは変えない）
- **部門ラベルの照合（Issue #85）**: 設定の `departments[].label` が対象リポジトリのラベルに無いと、その部門の Issue は受付に置かれたままで気づきにくい。collector は起動したときに 1 回、そのあと 10 分ごと（`collector.config.ts` の `labels.intervalMs`。GitHub の 60 秒ごとの取得とは別の予定で、裏で走らせ、snapshot の周期を待たせない。前の照合が終わるまで次を始めない）に、`gh api --paginate --jq` で `repos/<r>/labels` の `name` だけを取り、行ごとに zod で検証する。照らし合わせは純粋関数 `missingLabelPositions`（`packages/collector/src/labels.ts`。設定の部門とラベル名の一覧から、無い部門の添字を返す。collector の内部の状態に頼らないので、設定の確かめ（#79）からも呼べる）で、比べ方は Issue のラベルを部門に結ぶとき（`build.ts`）と同じ完全一致（大文字と小文字・前後の空白・全角と半角も区別する）。無い部門があれば、状態ファイルに添字だけを `missingLabels`（昇順・重複なし・1 つ以上。全部あるときと、まだ分からないときは項目ごと書かない）で足す。ラベルの取得や検証に失敗したら「分からない」として扱い、「無い」とはしない。最後に取れた結果を残して、次に取れたときに置き換える（直れば消える）。失敗しても snapshot の更新と終了コードは変えない。`--once` でも、GitHub の取得と並べて 1 回照合する。ログは結果が変わったときだけ出し、添字・件数・種類だけにする（全部あれば `labels ok: 4/4`、無ければ `labels missing 1/4: departments[1] のラベルがリポジトリに無い` と次にやることの行、取れなければ `labels unknown: gh-failed`）。ラベル名・題名は出さない
- **部門の設定の取り違え（Issue #94）**: 形は正しいが中身が違う設定（例: `branchPrefixes` で広報と企画の接頭辞が入れ替わっている）は、書く前の確かめ（#79）だけでは防ぎきれないので、動きだしてから気づけるようにする。GitHub の取得が成功するたびに、同じ Issue と PR の一覧から純粋関数 `suspectedMixups`（`packages/snapshot/src/mixup.ts`。時刻を注入。部門の数を問わない）で判定する（`packages/collector/src/mixups.ts` が一覧を部門の添字に直して渡す。ブランチ名・ラベル名はそこで添字に変えて捨てる）
  - 数える PR: 直近 30 日（`MIXUP_WINDOW_MS`。ちょうど 30 日前と、いまちょうどは含む。いまより後（collector の時計が GitHub より遅れているとき）は次の取得まで待つ）にマージした PR で、ブランチ名が `branchPrefixes` で部門 i に当たり、結び付いた Issue（4.1 の結び付けと同じ規則）のうち部門ラベルがちょうど 1 つのものが、すべて同じ部門を指すもの。部門ラベルが無い Issue と 2 つ以上ある Issue は見ない。そうした Issue しか無い PR、Issue に結び付いていない PR、接頭辞で部門が決まらない PR、結び付いた Issue が別々の部門を指す PR（部門をまたぐ仕事）は数えない
  - 30 日をマージの日時（`merged_at`）で測るのは、collector が PR から取っている日時が `merged_at` と `closed_at` だけで取得を増やさずに済み、マージ済みの PR は結び付きが確定した成果物で、経験値の履歴（`history.mergedPrs`）と同じ範囲になるため。open の PR と、マージせずに閉じた PR は数えない（実装時の判断）
  - 疑う条件: 部門 i の数える PR のうち、別の 1 部門 j のラベルのものが 3 件以上（`MIXUP_MIN_COUNT`）で、かつ半分を超える（ちょうど半分は疑わない）。少ない件数での誤報を避けるため（社長の判断、2026-10-13）。過半数なので、1 つの i に j は 1 つまで
  - 知らせ方: 状態ファイル（4.1 の Issue #74）に添字の組だけを `suspectedMixups: [{ from: i, to: j }]`（`from` の昇順・重複なし・1 つ以上。無ければ項目ごと書かない。件数とラベル名は入れない）で足す。取得や検証に失敗したら、同じ collector の中で最後に成功した取得の結果を残す。前の状態ファイルからは読み戻さないので、起動し直した直後や `--once` で取得に失敗したときは書かない（#85 のラベルの照合と同じ。前のプロセスの結果を引き継がない）。`--once` でも、取得に成功すれば書く。ログは結果が変わったときだけ出し、添字と件数だけにする。i→j と j→i の両方があれば `mixups suspected: departments[1] と departments[2] が入れ替わっているかもしれない（直近 30 日のマージ: departments[1] の接頭辞の PR 3/4 件が departments[2] のラベルの Issue、…）`、片方だけなら `mixups suspected: departments[3] の接頭辞の PR 3/4 件が departments[0] のラベルの Issue に結び付いている（直近 30 日のマージ）`。続けて次にやることの行を出す。疑いが消えたら `mixups ok` を 1 回出す（起動して何も疑わないときは出さない）
- **ログ**: 出すのは件数・時刻・エラーの種類だけ（履歴は `history: opened=… completed=… merged=…` の件数だけ）。題名・本文・ブランチ名・パス・セッション ID はログに出さない。`failed: gh-failed` の次の行には、次にやること「次にやること: guild.settings.local.json（無ければ guild.settings.json）の repo を gh のアカウントで読めるか、gh repo view <owner/name> で確かめてください」を出す（Issue #74）。リポジトリ名もログに出さない方針なので、`<owner/name>` は書いたまま出す。セッションの行（`sessions=5 ok` / `sessions unavailable: parse-failed`）は 5 秒ごとには出さず、変わったときだけ出す

### 4.2 snapshot.json の中身

```
{
  schemaVersion: 3,
  fetchedAt: ISO 8601,                 // GitHub を取った時刻（60 秒ごと）
  repo: "owner/name",
  issues: [{ number, title, labels: string[], state, createdAt, updatedAt, closedAt | null }],
  prs:    [{ number, title, state, mergedAt | null, closedAt | null, headRef,
             linkedIssues: number[], changedFiles: string[] }],  // changedFiles は open PR だけ。closed は []
  history: {                           // 全履歴（4.1）。番号と部門だけ
    openedIssueCount: number,          // 開かれた Issue の総数（open + closed。閉じた理由を問わない）
    completedIssues: [{ number, departments: ("経理" | "広報" | "企画" | "総務")[] }],   // completed で閉じたもの
    mergedPrs: [{ number, linkedIssues: number[], branchDepartment: "経理" | … | null }]
  },
  sessions: { status: "ok", checkedAt: ISO 8601,       // セッションを読んだ時刻（5 秒ごと）
              members: [{ department: "経理" | "広報" | "企画" | "総務" | null,   // null はかなめ
                          state: "awaiting-permission" | "working" | "resting" | "idle" }] }
          | { status: "unavailable", checkedAt: ISO 8601 }
}
```

本文とコメントは保存しない。MulmoTerminal のセッション ID とパスも保存しない（部門と状態だけ）。`members` はかなめと 4 部門のちょうど 5 件（セッションが無い席は `idle`）。

`history` には題名・部門以外のラベル・ブランチ名・日時を入れない（経験値を数えるのに日時は要らない）。番号は一覧の中で重ならず、completed の Issue の数は開かれた Issue の総数を超えない（schema で確かめる）。いまの規模で 1 件 30〜60 バイト × 約 300 件 ≒ 15 KB 増える。

`schemaVersion` は M3 で 2 に上げた（`sessions` を足したため）。Issue #19 で 3 に上げた（`history` を足したため）。古い版の snapshot（古い collector が書いたもの）は、画面が「収集スクリプトを更新してください」で止める。

### 4.3 画面の取得と表示

- 画面は 5 秒ごとに `/snapshot.json` を `cache: 'no-store'` で fetch する（M3 で 30 秒から短くした。手元の no-store の読み込みなので軽い）。ネットワークエラーと HTTP エラーの両方を扱い、失敗したら前回の表示を残して小さく「取得失敗」と出す
- **まだ集めていない（Issue #67）**: 204 No Content は、collector がまだ一度も snapshot を書いていない印として、HTTP エラー（404・500 など、`reason: 'http'`）と分けて `reason: 'not-collected'` にする（204 も `ok` なので、その判定より前に見る）。404 ではなく 204 にしたのは、ブラウザが失敗した fetch を 5 秒ごとにコンソールのエラーとして記録し、初めて触る人に壊れて見えるため。最初の snapshot を表示する前に 204 なら、エラーを出さずに自動のデモ（4.11）に切り替える（社長とメンターの判断「だれでも起動だけで見える状態に」）。自動のデモの間も裏で 5 秒ごとに `/snapshot.json` を読み、204 以外が返ったら再読み込みなしで本物の画面に切り替える（500・404・ネットワーク・検証失敗なら、本物の画面がこれまでどおりエラーを出す）。切り替えは画面（`ui/GuildScreen.vue`）を作り直して行い（`app/screenMode.ts`）、デモの状態を本物に持ち込まない。切り替えを決めた取得の結果は、新しいストアの最初の結果としてそのまま渡す（読み直すと 204 が返ってデモに戻り、エラーが一度も出ないことがあるため）。エラーを出した後の取得で 204 が返れば、まだ集めていないので自動のデモに戻る。自動のデモの後の本物のストアは、最初の正常な snapshot を localStorage の基準と比べずに新しい基準として保存する（古い基準が残っていると、切り替え直後に出来事がまとめて出るため。社長の判断）。新しい基準を保存できるまで（localStorage が一時的に使えないときも）この扱いを続け、それまでのエラーでは保存済みの基準に触れない（エラーで切り替わって 204 でデモに戻ったとき、正常な snapshot を受け取らないまま基準を失わないため）。一度 snapshot を表示した後の 204（ファイルを消したなど）は、前回の表示を残して「取得失敗（データのファイルがありません）」と出す（デモにはしない）。ビルドは架空の `snapshot.sample.json` を読むので、204 にはならない
- **外部へのリンク（Issue #67）**: 自動のデモの帯の docs/setup.md へのリンクは、開発サーバーが `docs/` を配らないので GitHub の公開ページ（conect-guild 自体のリポジトリ。URL は `apps/web/src/project.ts` の定数 1 か所で、チームの設定ファイル（`guild.settings.local.json`・`guild.settings.json`）とは別）にし、`target="_blank"`・`rel="noopener noreferrer"` で開く。「ブラウザから外部へ通信しない」は画面が自分から外部と通信・外部の資源を読み込むこと（fetch・img・フォント・スクリプト）を禁じるもので、見る人がクリックしたときにだけ開くリンクはこれに当たらない（社長の判断、2026-10-12）
- `schemaVersion` が画面の想定と違えば、表示を止めて「収集スクリプトを更新してください」と出す
- 開発時（実データ）は snapshot の `repo` が読み込んだ設定ファイル（`guild.settings.local.json`、無ければ `guild.settings.json`）の `repo` と違えば、表示を止めて「収集の対象と設定が違います」と出す（設定を変えた直後、新しいリポジトリの収集が成功するまで前のチームのデータを新しい名前・部門で出さないため）。build のダミーは照合しない
- `fetchedAt`（GitHub の取得時刻）が 5 分より古ければ「情報が古い」の印を出す（collector が止まっている合図）。セッションの状態の古さは別に `sessions.checkedAt` で見る（4.7）
- 開発時だけ、Vite の自作プラグイン（`configureServer` のミドルウェア。依存なし）が `/snapshot.json` を `apps/web/.data/snapshot.json` から返す。ファイルが無ければ 204 No Content（`Cache-Control: no-store`、本文なし。画面は「まだ集めていない」として自動のデモにする）、ほかの読み込みの失敗は 500。`.data/` は `public/` の外なので、Vite の public 監視による再読み込みは起きない。同じプラグインが `/collector-status.json` を `apps/web/.data/collector-status.json` から同じ決まり（`no-store`、無ければ 204、ほかの失敗は 500）で返す（Issue #74）
- **collector の状態（Issue #74）**: 自動のデモ（4.11）の間だけ、始めたときと、裏で `/snapshot.json` を読んで 204 だったたびに、`/collector-status.json` を `no-store` で読んで zod で検証する（`adapters/collectorStatus.ts`）。204 は「状態ファイルが無い（collector を動かしていない）」、検証できた状態はそれに置き換え、ほかの失敗（ネットワーク・HTTP エラー・壊れた JSON・合わない形）は前に読んだ状態を残す（1 回の読み損ないで帯がちらつかないように）。状態の読み込みは `/snapshot.json` の読み込みを待たせない（状態が応答しなくても本物への切り替えが遅れないように）。読み込みには番号を振り、後から始めたものを反映した後に終わった古い応答は捨てる。読み損ないは何も確定させないので、その前に始めた有効な応答は後から届いても反映する。帯に出すかどうかは純粋関数 `domain/collectorStatus.ts` の `collectorFailureOf`（時刻を注入）で決める: 状態が無い・成功・`attemptedAt` が 5 分（`STALE_AFTER_MS`。collector は 1 分ごとに試すので、それより古いのは collector が止まった後）より古いときは出さず、それ以外の失敗は種類を出す。本物の画面（snapshot を表示した後）では読まず、「情報が古い」などの表示はこれまでどおり
- **部門ラベルの食い違い（Issue #85）**: 本物の画面（`?demo=1` と自動のデモでは読まない）は、5 秒ごとに `/collector-status.json` を読み（`app/labelWatch.ts`、`app/useMissingLabels.ts`）、`missingLabels` があれば画面の上に帯「部門のラベルがリポジトリにありません: 広報（departments[1]）。この部門の Issue は受付に置かれます」と、docs/setup.md の直し方へのリンクを `--danger` の色で出す（自動のデモの帯と同じ形）。状態ファイルには添字しか無いので、ラベル名は画面が読んだ設定から引く（`domain/missingLabels.ts`）。読み損ないは前の状態を残し、204 は消す。`attemptedAt` が 5 分（`STALE_AFTER_MS`）より古ければ、collector が止まった後として出さない。上の自動のデモの間の読み方は変えない
- **部門の設定の取り違え（Issue #94）**: 同じ状態ファイルの読み込み（`app/labelWatch.ts`）で `suspectedMixups` を読み、画面の上に帯を `--danger` の色で出す（`ui/MixupsBanner.vue`）。両方向の組は「部門の設定が入れ替わっているかもしれません: 広報（departments[1]）と企画（departments[2]）の接頭辞の PR が、互いに相手のラベルの Issue に結び付いています」、片方向は「…: 経理（departments[0]）の接頭辞の PR が、総務（departments[3]）のラベルの Issue に結び付いています」。ラベル名は画面が読んだ設定から引き（`domain/mixups.ts`）、設定に無い添字の組は出さない。docs/setup.md の直し方へのリンクを付ける。古さ・読み損ない・204 の扱いはラベルの食い違いと同じ。帯は 1 本だけなので、ラベルの食い違いがあればそちらを先に出し、直ればこちらが出る

### 4.4 差分 → イベント（domain/events.ts, domain/baseline.ts）

- 差分の基準はブラウザの `localStorage` に置く。保存するのは `{ schemaVersion, fetchedAt, repo, issues: [{ number, state, closedAt }], prs: [{ number, state, mergedAt }], levels: { kaname, minori, hibiki, hirame, sasae } }` だけ。`repo` はリポジトリ名の FNV-1a（32 bit）の値で、名前そのものは保存しない。`levels` は各メンバーのレベルの数字だけ（王様は持たない。4.6）。題名・ラベル・ブランチ名も保存しない
- **初回**（基準が無い、`schemaVersion` が違う、または基準の `repo` が今回のリポジトリと違う。設定ファイルの `repo` を変えた直後など）は演出を出さず、基準だけ保存する。`repo` を足したので基準の `schemaVersion` を 2 にした（1 の基準は初回扱い）。`levels` を足したので 3 にした（2 の基準は初回扱いなので、更新後の最初の 1 回は全員そろって何も出さずに基準になる）
- **巻き戻さない**: 今回の `fetchedAt` が基準の `fetchedAt` 以前なら、イベントも基準の更新もしない
- **空白が長いとき**: 基準の `fetchedAt` が 7 日（収集の取得範囲）より古ければ、取りこぼしがありうるので演出を出さず、基準だけ置き換えてメッセージ窓に「この期間の出来事は復元できません」と出す。レベルアップ（4.6）だけは出す（レベルは全履歴から数え直すので取りこぼさない）。お知らせの後に出す
- **基準の更新**は、取得と検証に成功したときだけ行う。失敗した取得では基準を変えない
- **イベント**: 基準と今回を比べて、「Issue が新しく開いた → 部門あり: かなめが巻物を担当の机まで持っていって手渡し、担当は席で作業を始める（近い机には、ときどき受付から投げて渡す。8 章）／部門なし: かなめが受付で巻物を受け取る」「PR がマージ → 部門あり: 担当が宝箱を受付のかなめに届けて席に戻り、かなめが宝箱を掲げる／部門なし: かなめが受付で宝箱を掲げる」「Issue がクローズ → メッセージ窓に『クリアした！』を出し、担当の席の上に紙吹雪」を出す。部屋から出ていく演出（扉からの出発・帰還）はしない。扉は飾りとして残す
- **基準に無いまま閉じたもの**: 取得の間に開いて閉じた Issue（基準に無く、今回 closed で `closedAt` が基準の `fetchedAt` より後）はクリアだけを出す。マージ済みで基準に無い PR も同じく宝箱の受け渡しだけを出す
- **重複を出さない**: イベントは「種類 + 番号」（例: `issue-closed#123`）で識別し、同じ基準から同じイベントを二度出さない。イベントを出したあと、その取得の内容で基準を置き換える
- **localStorage が使えない**（例外、容量不足、プライベートモード）ときも表示は続け、演出だけ出さない

### 4.5 担当の決め方（domain/quest.ts, domain/party.ts）

- **Issue の担当**: 部門ラベル（`経理`・`広報`・`企画`・`総務`。読み込んだ設定ファイル（`guild.settings.local.json`、無ければ `guild.settings.json`）の `departments`）で決める
  - 部門ラベルが 0 個 → 「かなめの受付（担当なし）」の巻物として受付に置く
  - 2 個以上 → 固定の順（設定ファイルの `departments` の並び順。既定は経理 → 広報 → 企画 → 総務）で最初のものを担当にし、巻物に「複数部門」の印を付ける
- **PR の担当**: 次の順で決める
  1. `linkedIssues` のうち snapshot にある Issue の部門ラベル（複数あれば上と同じ固定の順）
  2. 結べなければ、ブランチ名の接頭辞の対応表（設定ファイルの `branchPrefixes`。上から順に見て最初に当たったもの）で推定
  3. それも無ければ「担当不明」として、かなめの受付に置く
- **PR の待ちの種類**（open PR だけ）
  - `changedFiles` のどれかがルール変更に当たる → 社長の承認まち（conect-management のルール変更は社長がマージするため）。照合は glob を使わず、文字列比較で行う。規則は読み込んだ設定ファイル（`guild.settings.local.json`、無ければ `guild.settings.json`）の `ruleChangePaths` に、`exact`（等しい）・`suffix`（で終わる）・`prefix`（で始まる）のどれかとパスの組で書く。既定は次の 3 つ
    - パスが `CLAUDE.md` に等しい（ルートの CLAUDE.md）
    - パスが `/CLAUDE.md` で終わる（`accounting/CLAUDE.md`、`projects/CLAUDE.md` など）
    - パスが `.claude/agents/` で始まる
    - テスト例: `CLAUDE.md`・`pr/CLAUDE.md`・`.claude/agents/pr.md` は当たる。`CLAUDE.md.bak`・`docs/MYCLAUDE.md`・`x/.claude/agents/a.md` は当たらない
  - それ以外 → かなめの確認まち

### 4.6 状態の導出（domain/party.ts）

メンバーの状態は、上から順に最初に当たったもの（優先順位: 社長の承認まち > かなめの確認まち > working > done > idle）。

| 優先 | メンバーの状態 | 条件（GitHub だけで分かる範囲） |
|---|---|---|
| 1 | 社長の承認まち | 自分が担当の open PR のうち、ルール変更のファイルを含むものがある |
| 2 | かなめの確認まち | 自分が担当の open PR がある（1 に当たらないもの） |
| 3 | working | 自分が担当の open Issue がある |
| 4 | done | 直近 N 分（既定 30 分）に自分が担当の Issue がクローズされた |
| 5 | idle | 上のどれでもない |

判定に必要な値が欠けているとき（例: 対応表に無いラベルだけの Issue）は idle にし、理由をツールチップに出す。

M3 からは、セッションの状態（4.7）を混ぜる。優先順位は 許可待ち（リアルタイム） > 社長の承認まち > かなめの確認まち > いま作業中（リアルタイム） > working > done > idle。リアルタイムの 2 つは、パーティの窓に「許可待ち」「いま作業中」と点滅する印付きで出し、ツールチップに MulmoTerminal から読んだことを書く。一区切り（resting）と待機（idle）のセッションは GitHub だけで決める。かなめも同じ考えで、許可待ち > PR の確認 > いま作業中 > 受付 > 待機。社長にはセッションが無いので変わらない。セッションの状態が取れないか古いときは、M2 までと同じく GitHub だけで決める。

「最近の成果」= 自分が担当の、直近 7 日にマージされた PR の数（domain/reward.ts。テストで固定）。取得範囲に合わせた値なので、時間がたつと減る。

**累積の経験値とレベル**（M4、Issue #19。社長の判断、2026-10-12）。collector が全履歴を毎回数え直して snapshot の `history`（4.1、4.2）に入れ、経験値は画面の domain で数える。PR は 3 本に分ける: 1) collector と schema（済み）2) 経験値とレベルの表示（済み）3) レベルアップの演出と E2E

- 経験値: 担当の Issue のクリア（completed で閉じたもの）10、担当の PR のマージ 5。「Close as not planned」は数えない。担当の決め方は 4.5 と同じ（Issue は部門ラベルの固定の順の先頭、PR はリンクした Issue の部門 → ブランチの部門）。リンクした Issue の部門は、履歴の completed の Issue と今の `issues` から引く。not planned で閉じて 7 日を過ぎた Issue はどちらにも無いので、それだけにリンクした PR はブランチの部門になる（それも無ければ、だれの経験値にもしない）
- かなめ: 受付で配った巻物（開かれた Issue。`openedIssueCount`）1 件につき 3 ＋ 担当なしの Issue のクリア 10（担当なしだけだとかなめのレベルが上がらないため）
- 担当の分からないマージ済みの PR（リンクした Issue にもブランチにも部門が無い）は、だれの経験値にもしない。かなめの経験値は上の独自の基準だけで、PR を足さない（「最近の成果」と同じ扱い。実装時の判断）
- 王様はレベルを持たない（「おうさま」と出す）
- レベル L に要る累積の経験値は 5 × L × (L − 1)（上限 99）
- 表示: パーティの窓に Lv と次のレベルまでのゲージ。Canvas にも席の足元に小さく薄く常時出す（控えめに）
  - パーティの窓（domain/xp.ts → app/partyLevel.ts → ui/PartyStatus.vue）: 名前の行の「成果 N」の左に「Lv N」、その下に細いゲージ（CSS の幅だけ）。王様は「おうさま」でゲージなし。ツールチップに「けいけんち 45・つぎのレベルまで 15（クリア 3 件・マージ 3 件）」のように件数だけを出す（かなめは「受付の巻物 24 件・担当なしのクリア 2 件」、99 では「レベルは さいこう」）。題名は出さない。ゲージは 1 行目の高さに収め、右の列の高さ（3 章 map.ts の 340px）を変えない（E2E で確かめる）
  - Canvas（render/levelTags.ts・drawLevelTags.ts）: 席の足元、つまり机（かなめは受付台）の前面に `fillText` で「Lv N」を小さく（10px）薄く（不透明度 0.7）出す。文字には暗い縁取り（`strokeText`）を付ける。机の木目の上と夜の暗さの中で読めるようにするためで、描くのは画面の中で作った「Lv」と数字だけ（外部の文字列ではない）。席の位置に固定し、席を離れて歩いている間も机に残る。頭の上の吹き出しと窓には重ならない（テストで確かめる）。かなめの分もほかと同じく受付台の前面の中央に出す（物を届けに来た人が中央の前に立つ間は隠れてよい）。夜の暗さの後に描き、吹き出しと同じくどの時刻でも同じに読める。狭い画面で Canvas が隠れている間・halted の間（Canvas はぼかしたまま）は吹き出しと同じ扱い
  - サンプル（`snapshot.sample.json`）では、かなめ Lv 4（92）、みのり Lv 3（45）、ひびき Lv 2（25）、ひらめ Lv 2（25）、ささえ Lv 3（35）
- レベルアップ: クリア等のメッセージの後に「〇〇は レベル N に あがった！」、効果音、席で跳ねて紙吹雪。初回・レベルが下がったときは出さない
  - 判定（domain/levelUp.ts、domain/events.ts）: 差分の基準（4.4）の `levels` と今回のレベルを比べ、上がった人ごとにイベント `level-up` を 1 つ出す。2 つ以上上がっても 1 回だけで、上がった先のレベルを言う。下がったとき（ラベルの付け替え、再オープン）は何も出さず、基準のレベルだけ下げる。同じ取得で複数の人が上がったら、かなめ → みのり → ひびき → ひらめ → ささえの順に 1 人 1 行。巻き戻し・初回・リポジトリ違いの扱いは 4.4 のまま。halted から戻ったときは、止まる前の基準と比べて上がっていれば出す（クリアなどと同じ）。純粋関数で、vitest で守る
  - メッセージ窓: 同じ差分のクリア・宝箱・巻物のメッセージの後に置く（「クリアした！」→「レベル 4 に あがった！」の順で読める）。名前は読み込んだ設定ファイルから取り、番号・題名は入れない
  - 効果音: オリジナルの楽譜 `levelup`（4.8）
  - Canvas（render/levelUp.ts、drawLevelUp.ts）: 本人が席で 2 回跳ね（立ちのコマを上下にずらすだけ。1 回 0.42 秒、高さ 12px）、席の上に紙吹雪（クリアと同じ）と「LEVEL UP」の文字（固定の文字列を `fillText`、暗い縁取り付き）を紙吹雪と同じ 2.6 秒出す。文字は少しずつ上がり、終わりの 0.6 秒で消える。かなめは受付で同じことをする。新しい絵は足さない。跳ねるのは描く位置だけで、足元（席・奥行き・席にいるかの判定）は変えない。夜の暗さの後に、吹き出しや紙吹雪と同じく一番上に描く
  - 席にいないとき: 巻物・宝箱の演出の配役と同じく、本人を演出の配役にする。ほかの演出の途中なら、席に戻るのを待ってから席で跳ね、メッセージもそれまで待つ（6 章 M2 の配役待ち）。紙吹雪だけのクリアと違い、跳ねる間は本人の動きを預かるため
  - 遊びに出ているとき: レベルアップのメッセージがキューに入った時点で、本人は席へ歩いて戻り始める。メッセージはキュー（app/messageQueue.ts）が Canvas から受け取った「席に戻るまでの時間」だけ待ってから窓に出る（キューが空でも待ち、その間の窓はナレーションのまま。待っている間の ▼ は効かない）。メッセージ・効果音・跳ねるのが同じ時刻に始まる。Canvas がまだ動いていない（絵の読み込み中）・隠れている（狭い画面）・ページが非表示のときは待たない。ほかの出来事は今までどおり、メッセージの後で席に戻ってから演出が始まる（8 章 #23）
  - 王様の呼びかけの返事（4.10）が「LEVEL UP」の間に来たら、文字を返事の吹き出しの上へずらす。返事は演出中のほかの人と同じくその場でさせる（4.10 の規則のまま）

### 4.7 セッションの状態（M3。domain/session.ts、packages/collector/src/sessions.ts）

社長の判断（2026-10-12）で、Claude Code の hooks は足さず、MulmoTerminal（v8.8.0 で確認）がもともと書いているファイルを collector が読む。5 セッションの `~/.claude/settings.json` には触らない。

**読むファイル**（`collector.config.ts` に固定。読むだけで、書かない・ロックしない）

- `~/.mulmoterminal/dev-terminal-cwds.json`: 名前は .json だが中身は行ログ。1 行が `<セッション ID> <絶対パス>`。グリッドのセルが接続したとき、新しい ID か cwd が変わったときに追記される。同じ ID が何度も出たら最後の行が正
- `~/.mulmoterminal/activity-state.json`: `{ "<ID>": { working, waiting, event } }`。作業中か待ちのセッションだけが残り、暇なセッションは消える。時刻は持たない

**会社以外を捨てる**

- 会社の 5 セッションの起動ディレクトリを読み込んだ設定ファイル（`guild.settings.local.json`、無ければ `guild.settings.json`）の `commanderSessionDir` と `departments[].sessionDir` に固定する。既定（`guild.settings.json`）は `~/conect-management`（かなめ）、その下の `accounting`（経理）・`pr`（広報）・`planning`（企画）・`general-affairs`（総務）。`~/` はホームの下を表し、ホームは `os.homedir()` で決める。引数・環境変数では変えない。設定の検証（collector と画面に共通）で、`~`・`~/...`・絶対パスのどれかで、前後の空白・制御文字・末尾の `/`・空や `.`・`..` の区切りが無く、5 つの文字列が互いに違うことを確かめる。`~` とホームの絶対パスのように展開すると同じになる重複は、collector だけが起動時にホームを展開してから調べて止まる（画面はセッションの起動ディレクトリを使わない）
- 行ログは 1 行ずつストリームで読み、パスが 5 つに**完全一致する行だけ**を残す（末尾の `/`、子ディレクトリ、worktree は当たらない）。それ以外の行はその場で比べて捨て、変数にためず、保存も、件数を含めてログもしない。会社の ID が後で別のパスの行に出たら、その ID は会社の候補から外す（ID の最後の行が正）
- パスごとに、残った候補のうち最後の行の ID を今のセッションとする。行は MulmoTerminal と同じく前後の空白を落とし、最初の空白で ID とパスに分ける（パスの中の空白はそのまま）。ID が UUID の形でない行、空行、壊れた行は飛ばす
- 末尾の行（直後に改行が無い行）は書きかけかもしれない（MulmoTerminal は `\n<ID> <パス>` と行頭に改行を付けて追記するので、部門の行が会社のルートまでで途切れるとかなめの行に見える）。前回の周期でも同じ内容が同じ位置で末尾にあったときだけ使い、それ以外はその行を除いて決める。collector が覚えるのは末尾の行のハッシュと終わりの位置だけで、内容は持たない。新しいセッションの反映は最大 1 周期（5 秒）遅れる。`--once` では末尾の行を使わない
- activity-state.json からは、その ID のキーだけを引く。ほかのキーは見ない（壊れていても関係ない）。全体が JSON のオブジェクトであることと、会社のエントリの形（`working`・`waiting` が真偽値、`event` が文字列か null）を zod で確かめる
- snapshot に入れるのは部門（かなめは null）と状態だけ。ID とパスは入れない

**状態の規則**（上から最初に当たったもの）

| 条件 | 状態 | 画面 |
|---|---|---|
| `waiting` かつ `event === 'Notification'` | awaiting-permission | 許可待ち |
| `working` | working | いま作業中 |
| `waiting`（Stop・MarkedUnread など） | resting（一区切り） | GitHub で決める |
| エントリなし（セッションが行ログに無い場合も） | idle（待機） | GitHub で決める |

**読めないとき**

- 行ログか activity-state.json が無い、読めない、JSON として壊れている（MulmoTerminal は `fs.writeFile` で書き直すので、空や途中の JSON が見えることがある）、会社のエントリの形が違う → その周期の `sessions` は `unavailable`。GitHub の部分はそのまま書く。次の周期（5 秒後）に読み直す
- 行ログは 16 MB、activity-state.json は 1 MB を上限に読み、超えた分は読まずに `unavailable` にする（どちらもふだんは数十 KB 以下。5 秒ごとに全部読むので上限を置く。読んでいる間に増えても上限で止まる）
- ログは種類だけ（`missing`・`read-failed`・`too-large`・`parse-failed`・`invalid`）
- 画面は `sessions.checkedAt` が 30 秒より古ければ（collector が止まった）リアルタイムの状態を使わず、GitHub だけで決める。`unavailable` か古いときは取得の窓に小さく出す

**制約**（画面に出る状態の限界）

- MulmoTerminal で表示中のペインで終わった作業は、一区切り（resting）と待機（idle）を区別できない（どちらも GitHub で決めるので、画面の表示は同じになる）
- 携帯から許可に答えると、`Notification` が残ったままになることがある（次のイベントで直る）。その間は「許可待ち」と出る
- グリッドのセル以外で開いたセッション（ふつうのターミナルの `claude` など）は行ログに載らないので映らない
- MulmoTerminal の内部ファイルなので、版が上がると形が変わりうる。zod で確かめ、合わなければリアルタイムだけを止める（GitHub の表示は続ける）

**Canvas での見え方**（render/ambient.ts、render/bubbles.ts）

- いま作業中（busy）のメンバーは、かなめも含めて机で作業するアンビエント（タイピング）になる。許可待ちのメンバーは手を止めて見回し、席の上に青い「?」の吹き出しを出す（承認まちの「!」、確認まちの「…」と別の記号と色）
- 吹き出しはパーティの窓と同じ状態から決めるので、4.6 の優先順位どおり、許可待ちが社長の承認まち・かなめの確認まちより先に出る。新しい絵は足さない
- 吹き出しは席で待つ印なので、演出の間（巻物・宝箱を運ぶ、受付まで歩いて戻る、紙吹雪）は「?」「!」「…」とも隠し、席に戻ったら出し直す

### 4.8 効果音（M4。audio/、app/useSound.ts）

音のファイルは使わず、Web Audio の OscillatorNode と GainNode でファミコン風の電子音をその場で鳴らす。依存・素材・外部の読み込みは足さない（社長の判断、2026-10-12）。

| 場面 | 音（audio/scores.ts） | 鳴らす合図 |

| 宝箱を届ける（pr-merged） | C5 E5 G5 C6・G5 C6 の短いファンファーレ | 同上 |
| クリア（issue-closed） | ハ長調・ニ長調の分散和音を続けて E6 で伸ばすレベルアップ風 | 同上 |
| レベルアップ（level-up、Issue #19） | F5 A5 C6 F6 と駆け上がり、E6 F6 G6 A6 と上がって、G6 A6 から C7 を伸ばすオリジナルの旋律（約 1.1 秒。クリアより長く華やか。実在のゲームの曲に似せない） | 同上 |
| 許可待ち | 三角波で E6→A5 の 2 音 | 前回の party と比べて新しく許可待ちになった人がいたとき 1 回（何人でも 1 回）。同じ人が許可待ちのままなら鳴らさない。最初の snapshot で既に許可待ちの人は鳴らさない |
| 王様の呼びかけ（4.10） | 矩形波で D4→G4 の低い 2 音「ポ・ポン」（ほかのどの音より低い） | Canvas で呼びかけが始まった瞬間に 1 回（何人でも 1 回）。続けて来た指示は、前の呼びかけが終わって次の呼びかけが始まるときに鳴らす。ほかの音がまだ鳴っている間は鳴らさない（呼びかけの音のほうが譲る。出来事・許可待ちの音は知らせなので、呼びかけの音を待たずに鳴らす） |
| 文字送り | 小さな音量の C7 の「ピピピ」 | 出来事の無いメッセージ（お知らせ）が窓に出たとき。出来事のメッセージは出来事の音だけにし、2 つの音を重ねない |

- 楽譜は純粋なデータで、`toTones` が鳴らす時刻の並びに変える。どの出来事で何を鳴らすか、許可待ちの新規の判定、消音・非表示・halted での抑止は純粋関数（audio/judge.ts）で、vitest で守る。AudioContext は必要なメソッドだけのインターフェースで受け、テストでは偽物を注入する
- ブラウザは操作の前に音を出せないので、取得のようすの窓の「基準を消す」の行に「音を出す / 音を消す」と音量（3 段階）のボタンを置く（窓の高さは変わらない）。初期値は消音。設定（オン・オフと音量だけ）は localStorage の `conect-guild:sound` に残す。音を出す設定のまま開き直したときは、最初のクリックかキー操作で音が出るようになる
- ページが非表示の間と halted の間は鳴らさず、表示に戻っても鳴らさなかった音をまとめて鳴らさない。AudioContext が止まっている（suspended）間も鳴らさない（止まっている間に予約すると、再開したときにまとめて鳴るため）

### 4.9 ようすのナレーション（Issue #30。app/narration.ts、app/narrator.ts、app/useNarration.ts）

出来事のメッセージが無いあいだ（キューが空のとき）、メッセージ窓に「あたらしい できごとは まだ ない。」の代わりにギルドのようすを 20 秒ごとに入れ替えて出す（社長の要望、2026-10-12）。

- 文は 3 種類。A（ふだん）: 1 人ずつの今のようす。パーティの状態（4.6）と暇の段階（うとうと・ねむる・遊ぶ。遊びは行き先に合わせる）から作る。遊びは Canvas と同じく行き帰りの歩きを含むので、行きは「〜へ むかっている」、帰りは「せきに もどっている」と言い、目的地での動作（おちゃ・トイプードルと あそぶ・ながめる・おしゃべり）は滞在中だけ述べる。B（ときどき）: 朝・昼・夕・夜ごとの雰囲気。C（ときどき）: 直近 7 日のクリア数・宝箱の数・いちばん宝箱を集めた人。0 件の行は出さない。7 日の数え方は「最近の成果」（domain/reward.ts）と同じ
- 名前は読み込んだ設定ファイルから取る。王は「おうさま」、玉座のそばのペットは「トイプードル」と呼ぶ。題名・番号は使わない
- 選び方は純粋関数: 種類を重み（A 0.65・B 0.2・C 0.15。行の無い種類は除く）で、次に人（A は人を先に選ぶので、文の多い人に偏らない）、次に文を、注入した乱数で選ぶ。直前と同じ文は選ばない
- 遊びの行き先は Canvas と同じ値で決める: 暇の段階の人ごとの塩（idle.ts の seeds）を画面で 1 回だけ作って Canvas に渡し、Canvas は暇の始まりの時刻を知らせる
- 出来事のメッセージが来たらすぐそちらを出す。ナレーションはメッセージのキューに入らないので、演出との同期と ▼ の予約は変わらない。最後のメッセージが 30 秒で自動で閉じるか ▼ で閉じてキューが空になったら、新しいナレーションに戻る（6 章 M2）
- 入れ替えの 20 秒は、ページが非表示の間と halted の間は止まり、戻ると残りの時間から続く（出来事のメッセージの時計と同じ）。狭い画面ではメッセージ窓が見えているので止めない
- ナレーション中の ▼ は次のナレーションに進める。効果音（文字送りの「ピピピ」を含む）は鳴らさない（効果音はメッセージのキューだけを見る）

### 4.10 王様の呼びかけ（Issue #28。domain/summons.ts、render/summons.ts）

社長がかなめや部門のセッションに指示を出したら、画面では王様がその相手に話しかける（社長の要望と判断、2026-10-12。案 A）。

- **検出**: snapshot の sessions（4.7）で、かなめか部門のセッションが「待機（idle）・一区切り（resting）」から「作業中（working）」に変わった瞬間を、社長の指示とみなす（会社のセッションに話しかけるのは社長だけという前提）。読むのは状態の変化だけで、指示の中身は持っていない。許可待ちから作業中に戻るのは指示ではないので出さない
- **出さないとき**: 初回の読み込み、halted からの復帰（halted の間は前回の読み取りを忘れる）、セッションが `unavailable` か古い（30 秒、4.7）とき、前回の読み取りから 30 秒より空いたとき（情報が古い状態からの復帰）、今回の読み取りの時刻が前回より後でないとき（同じファイルの読み直し、時計の逆行。このときは比較元も前回のまま残す）。同じ状態が続く間と、作業中 → 待機は出さない。短い取得失敗（30 秒以内）のあとは比べ続ける。collector は 5 秒ごとに読むので、すぐ終わる指示は見逃すことがある
- 判定は純粋関数（時刻を注入）で、画面の取得ごとにストア（app/guildStore.ts）が 1 回だけ「誰に」を知らせる。同じ取得で複数のセッションが変われば、1 回の呼びかけで全員が返事をする
- **演出**: 王様が玉座で少し伸び上がって「！」（0.7 秒。叫びの形の吹き出し、4.12）、続けて「ゴニョゴニョ」（1.4 秒。ささやきの形）。そのあと呼ばれたメンバーが王様のほうを向いて「はっ！」（1.6 秒）。全部で約 3.7 秒。言葉は固定の文字列で、吹き出しは文字の幅に合わせる。時間は `render/metrics.ts` の `SUMMONS`
  - 横を向く絵しか無いので、玉座の左の席は右、右の席は左を向く。玉座の真下のかなめは後ろ向きの絵が無いので、正面のまま小さく跳ねる
  - 呼びかけは誰も歩かせない。席にいて演出の外のメンバーだけ向きを変える（返事を始めたときに描いていた位置に留めて向きだけ変え、手元の小物と暇の印を消す）。演出の途中（巻物を運ぶなど）や遊びに出ている・帰る途中のメンバーは、向きを変えずにその場で「はっ！」と返事をし、演出や歩きはそのまま続く（瞬間移動しない。席に戻るのを待つと返事が指示から 10 秒以上遅れるため）。席で返事をしている途中に巻物・宝箱の演出が始まったら、その人の返事はそこで終える（「はっ！」を消し、留めた位置も放して、演出はふだんどおり席から始まる。待ちの吹き出しを演出の間は隠すのと同じ扱い。席に戻っても返事はやり直さない）
  - 呼びかけは暇の時刻を書き換えない。暇の姿勢そのものは壁の時計で進むが、王様と席で返事をするメンバーは呼びかけの間その位置に留める（うとうとのうなずきや、うとうとから眠りに変わる境界でも跳ねない。続けて来た呼びかけでは、王様は最初の呼びかけの位置のまま）。遊びに出ているメンバーの暇の動き（行き帰りの歩き・滞在）はそのまま続き、その場で返事をする。寝ていた王様は寝ていた位置のまま起きて話し（呼びかけが終わるフレームでは、姿を描く前に暇の時刻を更新するので、寝姿に戻るちらつきは無い）、呼びかけが終わってから（続けて来たときは最後の呼びかけが終わってから）暇の時間を数え直す（#23。指示を出したのは王様なので、そのあとしばらくは起きている）。呼ばれたメンバーの暇は呼びかけでは数え直さない。セッションが作業中になればパーティの状態が変わって暇が終わり、遊びに出ていれば既存の動きで席に戻る（4.6、#23）。呼びかけそのものが帰り道を作ることはない
  - 呼びかけはほかの演出を待たせない（メッセージの送りは変わらない）。続けて来たら前の呼びかけが終わってから次を出す
  - 「はっ！」などは承認まち・確認まち・許可待ちの吹き出しや暇の印より優先して出す
- halted に入ったら、再生中の呼びかけと予約された呼びかけを捨て、halted の間は呼びかけを受け付けない。ページが非表示か Canvas が隠れている（狭い画面）間、開いた直後の絵の読み込み中に来た呼びかけは捨て、後から出さない。効果音は Canvas で呼びかけが始まったときに鳴らすので、捨てた呼びかけは鳴らない。途中で隠れた呼びかけは、戻ると続きから出す
- ナレーションとメッセージ窓には出さない（仕様に無いため）
- **かなめは玉座の横まで聞きに行く**（Issue #87。社長の提案と判断、2026-10-13。`render/visit.ts`）。司令塔は社長から案件を受け取る役なので、受付からではなく王様の近くで耳打ちを聞く。きっかけは上の検出と同じ（かなめのセッションが待機・一区切り → 作業中。中身は読まないので問いかけでも行く）
  - 流れ: 王様「！」（0.7 秒）→ かなめが受付から玉座の横のマスへ歩く（5 マス、1.25 秒）→ 到着を待って王様「ゴニョゴニョ」（1.4 秒）→ 「はっ！」（1.6 秒。かなめは横向きの絵で王様のほうを向く。到着から返事の終わりまで向いている）→ 受付へ歩いて戻る（1.25 秒）。全部で約 6.2 秒。王様は「！」のあと、かなめが着くまで黙って待つ。呼びかけはかなめが受付に戻ったときに終わる（続けて来た呼びかけはそのあとに出す。王様は戻るまで起きて座ったまま）。時間は `SUMMONS` と歩く速さ（`motion.MS_PER_TILE`）から決まり、経路は既存の経路探索（`findPath`）
  - 玉座の横のマスは玉座の左、前の列（`PLACES.throneSide`、14 列 4 行）。受付からの近さは左右で同じで、右の玉座の横にはペットが寝ているため左にした（実装時の判断）
  - 同じ取得で部門も呼ばれたら、部門は席で、かなめは玉座の横で、到着を待ってそろって「はっ！」と返す（1 回の呼びかけで全員が返事をする決まりのまま、返事の時刻を 1 つにするのがいちばん単純なため。部門の返事は #28 より約 1.25 秒遅れる）
  - 聞きに行くのは、呼びかけが始まるときにかなめが受付で手が空いているときだけ。演出の途中（巻物・宝箱・受付の紙吹雪）やその予約がある、遊びに出ている、遊びから帰る途中のときは、#28 のままその場で返事をして聞きに行かない（瞬間移動や長い待ちを作らない）。受付でうとうと・寝ているときは聞きに行く。聞きに行くのは演出と同じ扱いなので、かなめの暇の時間はそこで数え直す（戻ってすぐ寝姿や遊び先へ跳ねないため）
  - 聞きに行っている間に来た巻物・宝箱の演出は、既存の配役待ちでかなめが受付に戻ってから始まる。メッセージ窓もかなめが戻るまで待つ（Canvas が聞きに行かせたときに戻るまでの時間をメッセージの列に知らせ、レベルアップの呼び戻しと同じく待つ）。同じ取得で指示とかなめの要るメッセージが来て、そのメッセージがすぐ窓に出るときは、Canvas が指示より先にその演出を入れるので、かなめは演出の途中としてその場で返事をする（聞きに行かない。メッセージと演出がずれないため。E2E で守る）。デモ（4.11）でも同じ経路で動き、頭の 0.5 秒の指示でかなめが聞きに行くので、4.5 秒の巻物はかなめが戻る 7〜8 秒ごろに出る
  - halted に入って呼びかけを捨てたら、まだ歩き出していなければ受付に残り、玉座へ向かう途中や玉座の横にいればその場から受付へ歩いて戻る（帰り道に入っていればそのまま）。位置が中途半端に残ったり跳んだりしない。非表示・狭い画面・読み込み中に来た呼びかけは #28 のとおり捨てるので、聞きに行かない。途中で非表示になったら戻ると続きから。狭い画面で Canvas が隠れると演出と一緒に歩きも捨てるので、戻ったときに呼びかけが続いていれば、かなめは受付で返事をする。効果音は #28 のまま、呼びかけが始まる瞬間（「！」）に鳴らす

- **自動のデモ（Issue #67）**: `?demo=1` が無くても、`/snapshot.json` が 204（collector がまだ書いていない）なら同じ台本を自動で流す（4.3）。違いは 3 つ。「▶ はじめる」の窓を出さず、Canvas の準備ができたら台本を自動で始める。狭い画面（Canvas が隠れる）でも始め、縦に積んだ窓で掲示板・パーティ・メッセージが動く。見えない Canvas の演出だけを捨てる（Canvas が隠れている間の合図を捨てる既存の決まり）。狭い画面で「はじめる」を押せない `?demo=1` の決まりは撮影のためなので、そのまま。ブラウザはクリックの前に音を出せないので、音の設定は「音を出さない・音量 2」から始め（メモリだけ）、「♪ 音を出す」で鳴らせる。画面の上に小さな帯「デモ表示中（架空のデータ）。データを集めると自分のリポジトリに切り替わります」と docs/setup.md へのリンクを出す（帯のぶん画面の高さを詰める）。collector が失敗しているとき（4.3 の collector の状態）は、帯の文を「デモ表示中（架空のデータ）。collector が失敗しています（○○）。ターミナルを確認してください」に替え、`--danger` の色で出す。○○は種類を日本語で短くしたもの（`gh-failed` 認証・取得、`validation-failed` データの検証、`write-failed` ファイルの書き込み、`unexpected` 想定外のエラー）。成功が来れば今までどおり本物に切り替わる（Issue #74）。ブラウザのコンソールには、自動のデモを始めたときに `console.info` で案内を 1 行（「collector がまだデータを書いていないので、デモ（架空のデータ）を表示しています。npm run collect（または npm run dev:all）で集めると、自分のリポジトリに切り替わります」）、帯に出す失敗が変わったとき（出始めた・種類が変わった）だけ `console.warn` で帯と同じ文と種類（例: `（gh-failed）`）を出す。`console.error` は使わない（自動のデモの間コンソールのエラーが 0 件であることを E2E が確かめている。Issue #67）。基準・音の設定・暇の時刻は `?demo=1` と同じくメモリだけに置き、本物の localStorage に触れない

- **実データを読まない**: デモ中のストアは `/snapshot.json` を取りに行かず（`loadSnapshot` を差し替える）、台本が作る架空の snapshot だけを読む。題名・リポジトリ名（`demo-guild/demo-company`）・セッションの状態（MulmoTerminal の代わり）はすべてコードの中の固定値。collector は要らない

- **はじめる**: デモは「▶ はじめる」の窓から始まる。押すまでは台本の頭（掲示板は空）で止まる。押したクリックでブラウザが AudioContext を動かせるようになる（既存の「最初のクリックかキー操作で音が出る」仕組み）。台本の時計は押した時刻から数える。Canvas の絵の読み込みが終わるまでボタンは押せず「じゅんびちゅう…」と出し、Canvas が隠れる狭い画面（760px 以下）では「がめんを ひろげてください」と出して押せない。その間に押されても台本を始めない（読み込み中や Canvas が隠れている間に来た王様の呼びかけは捨てる決まり（4.10）なので、頭の呼びかけと効果音が欠けるため。統合レビューの指摘）。判定は app/demo.ts の `demoBlock`。Canvas が始められなかったとき（2D の描画が無いなど）も、エラーを出してから準備完了を知らせ、演出の合図は捨てる（app/stageBoot.ts）。窓・メッセージ・音だけでデモは進む

- 取得はデモだけ 1 秒ごと（ふだんは 5 秒）。台本の出来事を遅れなく拾うため

### 4.12 メンバーのセリフ（Issue #47。render/lineBook.ts、render/lines.ts、render/remarks.ts、render/murmurs.ts、render/overhead.ts）

メンバーが、出来事・状態の変わり目・暇なときに、短いセリフを Canvas の吹き出しで言う（社長の判断、2026-10-12）。3 本の PR に分け、1 本目で出来事の一言、2 本目で状態の変わり目の一言（承認まち・確認まち・許可待ちになったとき、ときどき）、3 本目でつぶやき（何も起きていない間、ギルド全体で同時に 1 人、40〜90 秒ごと、寝言を含む）を入れた。

- **セリフ**: コード（`render/lineBook.ts`）にメンバー ID ごと・場面ごとに置いた固定の文だけを使う。ひらがな・カタカナと「ー〜！？…、♪」だけで、最大 7 文字（8px の太字を 2 倍にした吹き出しで、玉座の左下のみのりの吹き出しが王様の吹き出しに届かない長さ）。漢字・数字・英字・「#」・空白は使わない（番号や題名が混ざったように見えるため）。名前は入れない（設定で名前を変えても文がずれない）。会社の実際の話に読める文（「くろじです！」「バズった！」など）は入れない。吹き出しが受け取る型は一覧の文字列リテラルの合併型で、snapshot から来た `string` は型の上で入らない。描くのは `fillText` だけ。通信も LLM も使わない
- **出来事の一言**（台本 `render/scenes.ts` が「誰がいつ話すか」を持ち、`render/director.ts` が台本を組むときに舞台の時計の上のセリフにする）:

| 出来事 | 誰が | いつ | 何秒 |
|---|---|---|---|
| 巻物を手渡す | かなめ | 担当の机の横に着いた瞬間（受け渡しまで） | 1.5 |
| 同上 | 担当 | 受け取って頭上に掲げ始めた瞬間 | 1.8 |
| 巻物を投げる（4.4、Issue #12） | かなめ | 手を離した瞬間 | 1.2 |
| 同上 | 担当 | かなめのセリフが終わった瞬間（受け取ったあと、掲げている間） | 1.8 |
| 部門なしの巻物・宝箱 | かなめ | 受付で掲げ始めた瞬間 | 1.8 |
| 宝箱を届ける | 担当 | 受付の前に着いた瞬間（受け渡しまで） | 1.5 |
| 同上 | かなめ | 受け取って掲げ始めた瞬間 | 1.8 |
| クリア | 担当（部門なしならかなめ） | 紙吹雪が始まった瞬間（遊びに出ていれば席に着いてから） | 2.0 |
| 同上 | 王様 | 担当のセリフが消えて 0.4 秒後（王様はクリアのときだけ反応する） | 1.6 |

  - 1 つの台本の中では順番に話す。前の人のセリフが終わるまで次の人は待つ（投げたときは巻物が 0.9 秒で届くので、担当はかなめの 1.2 秒が終わってから言う）。別の台本のセリフがまだ出ている人の番は、待たせずに捨てる（クリアが続いたときの 2 つ目の王様の一言など）
  - セリフは本人の頭上に出るので、別の演出で歩いている間にクリアが来たら、紙吹雪は席の上（今までどおり）、セリフは歩いている本人の上に出る（呼びかけの「はっ！」をその場で言うのと同じ考え方）
  - 時間は `render/metrics.ts` の `LINES`。どれも 1.2〜2.0 秒
- **状態の変わり目の一言**（`render/remarks.ts`、純粋関数）: 待ちの記号の吹き出し（4.7）が新しく出た人が、ときどき一言言う。社長の判断で毎回ではなく、注入した乱数が `LINES.remarkChance`（0.3）より小さいときだけ言う。言わないときは今までどおり記号の吹き出しだけで、言ったときも `LINES.remarkMs`（2.0 秒）で記号に戻る（記号は消さず、一言の間だけ隠れる）

| 新しく出た記号 | 誰が | 場面 |
|---|---|---|
| 「!」社長の承認まち | 担当 | `awaitPresident` |
| 「…」かなめの確認まち（かなめは PR の確認） | 担当・かなめ | `awaitKaname` |
| 「?」許可待ち | 担当・かなめ | `awaitPermission` |

  - 「新しく出た」は、前回の party と比べて記号が無かったか、別の記号だったとき（確認まちから承認まちに変わった人も言う）。同じ記号のままなら言わない。比べるのは Canvas に渡る party（GitHub とセッションの状態から決めたもの）だけで、題名や中身は使わない
  - 言わないとき: 最初の snapshot（その前の空の party とも比べない）、halted からの復帰（halted の間は比べる元を忘れる）、ページが非表示か Canvas が隠れている間（比べる元は更新し、あとから言わない）、本人が演出の途中・遊びに出ている・席へ帰る途中のとき（待たずに捨てる。席に戻ってから言うと変わった瞬間とずれるため）。言わなかった待ちは、同じ記号が続く間は次の取得でも言わない
  - 同じ取得で複数の人が新しく待ちになったら、パーティの窓の順に 1 人ずつ言う（前の人の一言が終わってから次の人。吹き出しを並べない）。前の取得の一言がまだ続いていれば、その後に続ける。party を受けるたびに、出ている途中・出る予定の一言のうち、待ちが終わった人や別の待ちに変わった人の分は捨てる（記号が無いのに待ちのセリフだけが出ないように。後ろの人の時刻はそのまま）。乱数は 1 人ずつ、言える人（席にいて演出の外）の分だけ引く
  - 一言は記号の吹き出しと同じく席で待つ印なので、演出の間は隠れる（時間は延ばさない）。レベルアップ（4.6）も、跳ねている間と紙吹雪・「LEVEL UP」の文字が出ている間は演出なので一言は隠れ、文字と重ならない（vitest で確かめる）。王様には Canvas の記号が無いので言わない
- **つぶやき**（`render/murmurs.ts`、純粋関数）: 何も起きていない間、ギルド全体で同時に 1 人だけが、今していることの一言を 2.4 秒言う。前のつぶやきが終わってから（最初は最初の snapshot から）、注入した乱数で 40〜90 秒（均等）待って次を出す。時間は `LINES.murmurMs`・`murmurGapMinMs`・`murmurGapMaxMs`

| 今していること | 場面 | 誰の文 |
|---|---|---|
| 席で作業がある（作業中・いま作業中。かなめは受付の仕事） | `work` | メンバーごと |
| 席で暇（待機・完了で、うとうとの前） | `idle` | メンバーごと。王様は承認まちでないとき |
| うとうと（暇が 10 分から） | `doze` | みんなで同じ |
| 寝ている（暇が 30 分から） | `sleepTalk`（寝言） | みんなで同じ。王様だけ自分の寝言 |
| 遊び先に着いて滞在中（おちゃ・トイプードル・おしゃべり） | `tea`・`pet`・`chat` | みんなで同じ |
| 窓辺に滞在中 | 朝 `windowMorning`・昼 `windowDay`・夕 `windowEvening`・夜 `windowNight` | みんなで同じ。時間帯はナレーション（4.9）と同じ区切り（`daylight.dayPhaseOf`。5〜9 時・9〜16.5 時・16.5〜19 時・それ以外）で、時刻は注入する |

  - 言える人: 演出の外（歩いて帰る途中も演出に数える）で、待ちの記号（「?」「!」「…」）が出ていない人。席にいるか、遊び先に着いて滞在している人だけで、遊び先への行き帰りの途中は言わない。王様は承認まち（ページの「承認まち」の吹き出し）の間は言わない。暇かどうかは Canvas に渡る暇の時刻（4.6、Issue #23）があるかで決め、遊びの行き先と滞在の時間は Canvas の暇の動きと同じ値（`idle.idleActivities`）を使う
  - 選び方: 言える人のうちから、直前につぶやいた人を除いて選ぶ。重みは寝ている人が 0.3（`LINES.sleepTalkWeight`）、ほかは 1。直前の人しか言えないときと、言える人がいないときは言わず、次をまた 40〜90 秒後にする。文は出来事の一言と同じ選び方（直近の 2 つを避ける）。みんなで同じ文は、人ごとではなくギルド全体で直近を避ける（別の人が今言った文を続けて言わない）
  - 後ろへずらす: 出来事の演出（レベルアップ・遊びからの帰り道を含む）・王様の呼びかけ・状態の変わり目の一言が出ているか出る予定の間は言わない。その間に出ているつぶやきは捨て、次のつぶやきは、それらが終わってから 2 秒（`LINES.murmurRestMs`）より前には出さない。それより後に予定していたつぶやきはそのまま
  - 言わないとき: 最初の snapshot の前、halted の間（予定も忘れ、戻ったら数え直す）、ページが非表示の間（舞台の時計ごと止まり、戻ると続きから）、Canvas が隠れている狭い画面（出ているものと予定を捨て、見えたら数え直す）
  - 頭上ではつぶやきは待ちの記号より下、暇の印より上。うとうとの「…」、寝ている「Z」、遊び先の「…」「♪」は、つぶやきの 2.4 秒だけ隠れる。演出に入った人のつぶやきは隠れる
  - デモ（`?demo=1`、4.11）は 1 周 60 秒のほとんどで演出か呼びかけが動いているので、つぶやきはその合間に、おおむね 1〜2 分に 1 回出る（開発サーバーで流して、5 分で 57・130・224・286 秒、別の回は 4 分で 114・224 秒に出た）
- **繰り返さない**: メンバー・場面ごとに、直近に言った 2 つ（候補が少ないときは候補の数 − 1 まで）を避けて、残りから均等に選ぶ（`lines.pickLine`、純粋関数）。乱数は紙吹雪・投げる判定とは別の源（`render/loop.ts` の `lineRandom`、本番は `Math.random`）から引き、注入した紙吹雪と投げる判定の乱数の列を進めない。直近に数えるのは実際に画面に出たセリフだけで（描いたフレームで覚える。halted や隠れた Canvas で捨てたもの、呼びかけの言葉に隠れ通したものは数えない）、1 つの発話は途中で呼びかけに隠れてまた出ても 1 回と数える。まだ出ていない予定のセリフも避け（続けて組んだ演出で同じセリフを選ばない）、直近の 2 つと予定を除いて候補が残らないときは、その回は何も言わない（直近のセリフを戻して言わない）。メンバーごとに同じ文を 2 つの場面に置かない（文から場面が分かる）。状態の変わり目の一言とつぶやきも同じ選び方・同じ乱数の源で、画面に出たものだけを直近に数える（つぶやきは、次までの間と誰が言うかもこの源から引く。待ちの記号や呼びかけに隠れ通したつぶやきは数えない）。みんなで同じ文（遊び先・うとうと・寝言）は、人ごとではなくギルド全体で直近を数える。履歴は Canvas の中だけに持ち、localStorage には残さない。メッセージの送り（`app/messageQueue.ts`）は台本を時間を数えるためだけに組むので、セリフを選ばない
- **頭上の優先順位**（`render/overhead.ts`）: 1 人の頭上には 1 つだけ出す。王様の呼びかけ（4.10）＞ 出来事の一言 ＞ 状態の変わり目の一言 ＞ 待ちの記号（「?」「!」「…」）＞ つぶやき ＞ 暇の印（「…」「♪」「Z」）。下のものは上のものが出ている間は隠れ、時間は延ばさない（出来事の一言の途中で「はっ！」が始まれば、その間は「はっ！」を出す）
- **吹き出しの形**（Issue #77、`render/bubbleShape.ts`・`render/drawBubble.ts`）: 社長の判断（2026-10-12）で、四角をやめて話し手を指す吹き出しにした。ふだんは白地に濃紺の 1px の縁、角を 2 段の階段で丸め、右下に薄い影を付ける。下辺から 4 段の階段の尻尾を出し、話し手の頭へ傾けて、頭に届く手前で止める。文字は 8px の太字（今までは 7px）で、横に 3px・上下に 2px の余白をとる（どれも 2 倍に拡大する前の大きさ）。意味で形を変える: 王様の呼びかけの「！」は叫びとして、黄色地・2px の縁・四隅と左右と上に出るギザギザ。「ゴニョゴニョ」とつぶやきはささやきとして、縁を点線にし、文字を灰色にする。待ちの記号（「?」「!」「…」）と暇の印（「…」「♪」）は、同じ形の小さな正方形に記号 1 つ。「Z」は今までどおり吹き出しなしで浮かぶ。Canvas は画面の幅に合わせて整数でない倍率で拡大するので、1 色ごとに重なる長方形を 1 本のパスにまとめて 1 回で塗り、段の間に細い横線が出ないようにする。描くのは図形と `fillText` だけ
- **重なり**（`render/overheadPlace.ts`、純粋関数）: 頭上に巻物・宝箱を掲げてセリフを言うときは、吹き出しを物の横（頭の高さ）に置き、尻尾を頭へ向ける。右 → 左の順に、ほかのメンバー（足元から上 72px・左右 16px）・ほかの吹き出し・机とカウンターの「Lv N」のタグ・HTML の窓にかからず、Canvas からはみ出さない所を選ぶ。どちらにも置けなければ、今までどおり物の上に出す（吹き出しを 34px 上げる。全員の掲げた物の上端より吹き出しの尾が上にあることを vitest で確かめる）。受付のかなめの横には上の段の机のタグが、席のみのり・ひびきの横には玉座と窓があるので、そこでは物の上になることが多い。言葉の無い記号は物の上に出す。置く順は、掲げていない人の吹き出しを先に決め、掲げた人の吹き出しはそれを避ける。1 つのセリフ（同じ話し手・同じ文・同じ種類が続けて出ている間）は、最初に決めた置き場所（物の横の左右か物の上）を使い続ける（隣の人が途中で離れても、物の上から横へ飛ばない）。ただし物の横に置いたセリフが途中で HTML の窓にかかるか Canvas からはみ出すようになったときだけ、置き直す。覚えるのは描いたフレームの置き場所だけで、描画のループ（`render/loop.ts`）が次のフレームに渡す（`overheadPlace.rememberPlaces`）。描く処理と「LEVEL UP」の文字の位置は同じフレームから同じ関数で決める。頭上に出す言葉の吹き出し（セリフと呼びかけの言葉）が机・カウンターの「Lv N」のタグ（Issue #19）にかかるときは、タグの 2px 上まで上げる（`overhead.overheadLift`。幅は文字数から見積もる）。低い席の長いセリフが、上の段の机やカウンターのタグに届くため（ひらめの 5 文字以上のセリフがかなめのタグに、かなめの 7 文字のセリフがひびきのタグに）。どの台本のどの瞬間もタグにかからないことを vitest で確かめる。言葉の吹き出しを頭の右上に出すと HTML の窓（いちばん伸びたときの大きさ、map.ts の `TALLEST_WINDOW_EXTENTS`）の下に入るときは、頭の左上に出す（`overhead.overheadSide`。ささえの席は右のパーティの窓の数マス左なので、長めのセリフが窓に入っていた）。どの吹き出しも窓にかからないこと、物の横に置いた吹き出しがほかのメンバーにかからないこと、王様の「！」「ゴニョゴニョ」がタグ・窓・画面の端にかからないことも同じテストで確かめる
- **止める・捨てる**: 舞台の時計に乗るので、ページが非表示の間は止まり、戻ると続きから出る。halted になったら、出ているセリフと出る予定のセリフを捨て、halted の間に始まった演出でもセリフを選ばない（台本の動きはそのまま）。狭い画面で Canvas が隠れている間は、台本と一緒に捨てる（4.4、6 章 M2）。halted の間と Canvas が隠れている間に始まった演出ではセリフを選ばないので、直近のセリフは見えたものだけになる。状態の変わり目の一言も同じで、halted になったら出ているものと続きを捨て、Canvas が隠れたら捨てる。ページが非表示の間は止まり、戻ると続きから出る
- メッセージ窓・ナレーション（4.9）・効果音（4.8）には出さない。セリフの文字は濃い色、つぶやきの文字は「ゴニョゴニョ」と同じささやきの灰色（吹き出しの形を参照）
- レベルアップ（4.6、Issue #19）の「LEVEL UP」の文字は頭上の優先順位に入れず、いちばん上に描く。その人の頭上に言葉の吹き出し（呼びかけの言葉かセリフ）があれば、描いた吹き出しの上端（`overheadPlace.wordsTop`。叫びのトゲと、物の横に置いた位置も含む）のさらに上に出す（クリアの直後にレベルアップが来て、クリアのセリフと重なるため）。レベルアップ自体のセリフはない
- デモモード（4.11）でも実データと同じ経路でセリフが出る（E2E で確かめる）

## 5. 公開範囲

- 実データ（`apps/web/.data/snapshot.json`）は Vite の `public/` に置かない。`.gitignore` で除き、パーミッションは 0600
- 実データを画面に出す経路は、開発サーバーの自作プラグインだけ。開発サーバーは `127.0.0.1` に固定し、`--host` に `127.0.0.1` 以外（`0.0.0.0` や値なし）を渡したり `server.host: true` を使ったりしない（LAN に出さない）
- `vite build` と CI は `apps/web/public/snapshot.sample.json`（架空の題名のダミー）だけを使う。プラグインは開発時だけ有効なので、ビルドに実データは入らない
- `dist/` は配布しない（GitHub Pages などに載せない）
- localStorage には題名を残さない（4.4）
- 実データを消すときは `apps/web/.data/` を消し、ブラウザの localStorage の基準を消す（画面に「基準を消す」ボタンを置く）

## 7. 依存の方針（具体）

- 実行時: `vue`、`zod`
- 開発時: `vite`、`typescript`、`vue-tsc`、`vitest`、`eslint` + `eslint-plugin-vue` + `eslint-plugin-sonarjs` + `typescript-eslint`、`prettier`、`@vitest/coverage-v8`（scoria にカバレッジを渡すため。Issue #33）、`@playwright/test`（画面の E2E。Issue #34）、`concurrently`（`npm run dev:all` で collector と開発サーバーを一緒に起動・停止する。Issue #70。推移依存の `shell-quote` は脆弱性 GHSA-pqg4-j6r4-53mv の直った版に `overrides` で固定し、`concurrently` がその版を取り込んだら外す）。ブラウザ本体は postinstall では入れず、`npx playwright install chromium` で明示的に入れる
- 入れ方:
  1. `npm install <pkg> --ignore-scripts --before=<7 日前の日付>` で npm に版を決めさせる（記憶から版を書かない）。`--before` で推移依存も含めて 7 日より前に公開された版だけになり、`--ignore-scripts` で確かめる前にスクリプトが走らない
  2. `npm view <pkg> time --json` で入った版の公開日を確かめる
  3. 公開から 7 日未満なら `npm install <pkg>@<1 つ前の版> --ignore-scripts` で固定し直す
  4. lockfile をコミットする。CI は `npm ci --ignore-scripts` で lockfile どおりに入れる
- 推移依存のインストールスクリプトは `npm query ':attr(scripts,[preinstall])'`・`[install]`・`[postinstall]` で確かめる。どうしても要るものだけ、理由を PR に書いて `npm rebuild <pkg>` で個別に実行する
- 追加・更新のたびに `npm outdated` と `npm audit` を見て報告
- 避けるもの: `postinstall` でスクリプトが走るもの、メンテナが 1 人で更新が止まっているもの、描画ライブラリ（最初は不要）
- 収集スクリプトの実行: Node の TypeScript 直接実行（型除去。Mac mini は Node v26.10、2026-10-12 確認）。`tsx` などの実行ランタイムは入れない。そのため collector は型を消すだけで動く構文に限る
  - `enum`・parameter properties・`namespace` を使わない
  - `packages/collector/tsconfig.json` に `erasableSyntaxOnly: true`、`allowImportingTsExtensions: true`、`noEmit: true`、`module: "nodenext"`（Vite 用の tsconfig とは分ける）
  - import は `.ts` 拡張子付きで書く

## 8. 絵の素材

- コンセプト画（codex 生成、`assets/concept/`）: 背景（M1）と目標の見た目として使う。生成の指示書も同じ場所に置く
- タイル（床・壁・机・本棚など 17 種）: codex にコンセプト画の雰囲気で生成させ、32px グリッドのシートに切り出す（`assets/tiles/`）。2026-10-12 の社長の判断で CC0 素材（Kenney など）から切り替えた。家具は原画の比率の大きさ（机 4×2、掲示板 3×2、椅子 1×2、窓 2×2、玉座 3×3、本棚 2×3、扉 2×3 マス）。受付のカウンターは左端・中央（くり返す）・右端の部品で 1 本に伸ばす。出所とライセンスを `assets/README.md` に書く
- 小物 51 種（`assets/decor/`）: 壁掛け・机の上・床置き・床のパッチを codex に生成させ、32px グリッドのシートに切り出す。部門ごとの小物（経理: そろばん・帳簿・金貨・金庫、広報: ポスター・メガホン・チラシ・イーゼル、企画: 地図の机・設計図・地球儀・模型、総務: ファイル・鍵掛け・道具箱）と共通の小物で部屋を埋める。小物の動きには新しい絵を描かず、揺らす・光らせる・小さな図形を重ねる範囲で動かす（`render/trinkets.ts`、Issue #11）。例外としてペットのトイプードルは眠る・起きてお座りの 2 コマを描き足した（社長の希望）
  - いつも: 灯りの火のゆらぎ、玉座の横のペット（トイプードル）の寝息（眠る絵 `sleeping-poodle` が 1px 上下する）と、たまに起きてお座りする動き（21 秒ごとに 1.68 秒だけ起きた絵 `awake-poodle` に差し替える。拡大縮小はしない。`render/trinkets.ts` の `petPoseAt`。誰かが遊びに来てそばに滞在している間は起きてお座りしたまま。Issue #39）、床の光（light-patch）が日の動きに合わせて朝は左・夕方は右へずれ、夜は消える
  - 部門が作業中（working / busy）の間: 経理のそろばんと金貨がきらっと光る、広報のメガホンから音符と「！」が出る、企画の地球儀に光の帯が横切る（回って見える）、総務はささえの机の書類の山の上の紙がずれ、角がめくれ、ときどき 1 枚ふわっと浮く（書類をさばいて見える）。右の壁の扉のそばの鍵掛け（key-board）はささえから遠く、総務の動きと分かりにくいので動かさない（2026-10-12、社長の指摘）
  - 部門の小物は本人が席にいる間だけ動く。演出で歩いている・受付にいる・遊びに出ている・遊びから帰る途中は止めて静止の絵に戻し、席に着いたらまた動かす（`render/director.ts` の `isAtSeat`、Issue #29）。砂時計（王様の合図）と旗（その側の壁、紙吹雪は席の上に出る）は本人の在席と関係がないので今のまま
  - 出来事で: 社長の承認まちの間は砂時計の砂が落ちる。砂時計は社長の承認まちの合図で、総務の作業とは関係ない（ささえの机に置いてあるが、配置は変えない）。Issue のクローズで紙吹雪が舞う間、その側の旗がはためく（奥の壁の旗はかなめ・経理・広報、左の壁の旗は企画・総務）。PR マージで金貨の山が増えるのは見送った（増えた量を覚えておく状態が要るため）
- 昼夜（M4、Issue #19）: ブラウザのローカル時刻で部屋の明るさを連続的に変える（`render/daylight.ts`）。朝・昼・夕・夜の 4 段階を目安に、色を部屋に掛け合わせる（昼はそのまま、夕方は橙、夜は暗い青）。夜はランタン・燭台・柱の灯りの周りだけが明るく、光の輪は火のゆらぎに合わせて少し伸び縮みする。窓のタイルは昼に明るく、夜は暗い。HTML の窓（掲示板など）、吹き出し、紙吹雪は暗くしない。描き直しはアンビエントの間引き（約 7fps）の中で、そのつど時刻を読む。開発時だけ `?hour=21.5` で時刻を固定して見られる

## 9. テストと CI

- domain は vitest で全関数をカバー（Issue → Quest の対応、ラベル 0 個・複数の扱い、PR の対応 Issue の拾い方、ルール変更のパス照合、状態の優先順位、差分 → イベントと重複の除去、初回・巻き戻し・長い空白・基準に無いまま閉じたものの扱い、最近の成果）。時刻と乱数は注入できるようにする
- adapters の検証は、壊れた JSON・`schemaVersion` 違い・localStorage の例外を食わせて落ちないことを確かめる
- collector は、複数ページの出力を平坦化できること、`gh` の出力の検証失敗時に snapshot を書き換えないことを確かめる
- ESLint（sonarjs の複雑度・ネスト・引数）をエラー、`max-lines` 400 / `max-lines-per-function` 60 を warning で入れる
- `npm run verify` = lint + typecheck + test。CI は push と PR で `npm ci --ignore-scripts` → verify → build（サンプルデータのみ）
- scoria でコードの健康状態を測る（Issue #33）。`.github/workflows/scoria.yml` が PR と main への push で `npm run test:coverage`（`coverage/lcov.info` を出す。遅いので verify には入れない）→ `npx -y scoria@0.3.0` を動かし、`.scoria/baseline.json` からの変化をジョブのサマリーに、指摘を SARIF で code scanning に出す。`mode: report` なので CI は落とさない。scoria は package.json に入れない（scoria 自身の依存の npm audit の警告がこのリポジトリのものに見えるため）
  - scoria の出力の「detection drift: vue is in the config but no longer detected」は誤検知で、計測には影響しない（Issue #50）。scoria 0.3.0 は stack をリポジトリ直下の package.json の依存だけで検出するが、vue は `apps/web/package.json` にある。計測は scoria.config.json の `stacks` に書いた値で行うので、`.vue` は数えられている。`stacks` から vue を外すと `.vue` の 8 ファイルと ui-consistency が測られなくなり、`targets` で workspace ごとに分けると knip・audit・coverage・circular が飛ばされる。依存を足さない設定では消せないため、そのままにする。案内に従って `scoria init` を実行しない（vue が外れる）。上流で workspace の package.json も読むようになれば消える
  - 循環 import の検査は、scoria が動かす madge が受け持つ。scoria は madge に tsconfig を渡さないので、リポジトリ直下の `.madgerc` で `apps/web/tsconfig.app.json` を渡す（Issue #44）。これが無いと madge は `.vue` の import を JavaScript として解こうとし、直前に読んだ `.js` の構文木を流用するか、`.vue` を JavaScript として読んで SyntaxError で止まる。止まると scoria は circular を測らないまま `complete: false` になる。どのファイルを先に読むかで結果が変わり、`coverage/` の HTML レポートがあると止まり、`apps/web/dist/` があると通っていた。通ったときも、`.vue` から拡張子なしで読む `.ts` の import（18 本）が依存のグラフから抜け、`.vue` を通る循環は見えていなかった
  - `.madgerc` は JSON で書く（コメント可）。先頭が `{` でないと INI として読まれるので、コメントは括弧の中に書く
  - scoria の実行結果で `complete: true` と「probes not scored」に circular が無いことを確かめる。原因は madge の依存（filing-cabinet・precinct）にあり、上流で直れば `.madgerc` は要らなくなる
- 画面の E2E は Playwright（Issue #34）。`npm run test:e2e` で動かし、遅いので verify には入れない。CI は verify と並行の別ジョブ e2e で、ブラウザを Playwright の版ごとにキャッシュして `npx playwright install --with-deps chromium` で入れ、失敗時はレポートを artifact に残す
  - 設定は `apps/web/playwright.config.ts`、テストは `apps/web/e2e/`。開発サーバーは 5196 番（`--strictPort`、host は vite.config.ts の 127.0.0.1）で、`--mode e2e` を付けて立て（手元の `guild.settings.local.json` があっても `guild.settings.json` を使うため。10 章 9）、既に動いているサーバーは使わない。chromium だけ、headless、retries は CI だけ 1。テストは 1 本ずつ順に動かす（アプリの 5 秒ごとの再取得を実時間で待つので、負荷で遅れないように）
  - データはダミーだけで、`apps/web/.data` には一切触れない（collector の実データを上書きしたり消したりしないため）。`/snapshot.json` は Playwright の `context.route` が全部横取りし、`public/snapshot.sample.json` を guild.settings.json の repo と固定した時刻に合わせたものを返す。テスト中の中身の差し替え（Issue を閉じる、別のリポジトリ）は route が返す値を変えて行う。横取りの印のヘッダーが無い `/snapshot.json` の応答（開発サーバーから来たもの）がページに 1 件でも届いたら、そのテストを落とす。これで `.data` に実データがあっても画面やレポートには出ない
  - 時刻は `page.clock.setFixedTime` で固定する（タイマーは動かし、5 秒ごとの再取得はそのまま）。音は AudioContext をページ内で偽物に差し替える
  - 確かめること: パーティの窓に Lv・ゲージ・内訳が出て、右の列が高くならない（Issue #19）、開いて console・ページのエラーが無い、掲示板・パーティ・メッセージ窓・取得のようすに値が出る、Canvas に部屋が描かれる（単色でない）、`?hour=12` と `?hour=21.5` で明るさが違う、「音を出す」と音量の切り替え（再読み込み後も残る）、「基準を消す」、760px 未満で窓が縦に積まれ Canvas が隠れる、別のリポジトリの snapshot で止まる、Issue を閉じると「クリアした！」が出る、メッセージ窓のクリックで次へ進み最後に閉じる、`?demo=1` で架空の題名と効果音が出て `/snapshot.json` を一度も取りに行かず localStorage に何も残さない（このテストだけは共通の横取りを使わず、`/snapshot*.json` へのリクエストがあれば落とす）

     - JSON にはコメントを書けないので、各項目の説明は docs/setup.md の 2-2 の表に寄せた
     - build に手元の値が入らないことは #76 のまま（build はプラグインが向けず、既定の JSON だけが入る）
   - 検証すること: 余分な項目が無い、6 人がそろう、色が `#rrggbb`、部門が 4 つ（Issue #18 まで）、ラベル・担当・起動ディレクトリ（書いた文字列のまま）が重ならない、起動ディレクトリに前後の空白・制御文字が無い、ブランチ接頭辞の部門が部門のラベルにある、`repo` が `owner/name` の形
   - 起動ディレクトリの `~` をホームに展開した後の重複は、共通の検証ではなく collector の起動時に調べて止める。画面は起動ディレクトリを使わないので、画面はそのまま動く
   - **手元の設定を書く道具（Issue #79）**: `npm run settings:write -- --dry-run | --write [--overwrite] [--json]`（`packages/collector/src/settingsWriteMain.ts`）。値だけの JSON（`repo`・`commanderSessionDir`・`departments[4]` の `label`・`sessionDir`・`prefix`）を標準入力から受け、検証して `guild.settings.local.json` を書く。書く・検証する土台で、値を集める入口（Claude Code のスキル）は別に作る（社長の判断）。ブラウザの画面では作らない（4.1 と同じく、ブラウザから GitHub に問い合わせず、開発サーバーに書き込みの口を作らない）
     - 出発点: いま読まれる設定（`loadSettingsFile`。手元のファイルがあればそれ、無ければ既定）。入力に無い項目は保つ。部門は 4 つまとめて置き換え、並びの i 番目の担当（`member`）は出発点の i 番目のまま（席がメンバーの id で決まるため）。メンバーの役（`role`）は、出発点で部門のラベルと同じだったときだけ新しいラベルに合わせ、手で変えた役は保つ。`branchPrefixes` は入力の接頭辞の 4 行を先に置き、出発点の行のうち部門のラベルが残っていて接頭辞が入力と重ならないもの（`docs/accounting-` など）をその後ろに保つ（実装時の判断）
     - 止めるもの（エラー）: 入力の形、合わせた結果の schema、5 つのフォルダが手元に無い（`~` はホームに展開して確かめる）、展開すると 2 つのフォルダが同じ、`guild.settings.local.json` があるのに `--write` に `--overwrite` が無い（Issue の「上書きは `--overwrite` か確認なしには行わない」。dry-run はその旨を出すだけ）
     - 警告にとどめるもの: ラベルがリポジトリに無い（#85 の `missingLabelPositions`。gh の呼び方は collector と同じ）、ラベルを問い合わせられない（gh の失敗・30 秒のタイムアウト。collector があとで照合するので、警告して書く。社長の判断）、取り違えの突き合わせ（部門のフォルダの `CLAUDE.md` にその部門のラベルの文字があるか、接頭辞の末尾の `/` を除いたものとフォルダ名が同じか）。雛形どおりでない会社もあるので止めない（社長の判断）
     - 部門の `CLAUDE.md` は、ラベルの文字を含むかの判定にだけ使い、中身は保存・表示・ログに出さない。結果は「見つかった・見つからない・読めない」だけ（社長の判断）
     - 出力: 人が読む確認の表（部門ごとにラベル・接頭辞・`CLAUDE.md` にラベルが見つかったか・フォルダ。フォルダは長いので行末に置き、ほかの列は幅を揃える）と警告・エラー。`--json` で同じものを JSON で出す（入口のスキルが読む）。外から来た文字（ラベル・パス）は JSON の文字列として引用し、制御文字などはエスケープして、端末に文字として出す
     - 書き方: 書くのは `JSON.stringify` の結果だけ（実行されるものは書かない）。前の手元の設定があれば、先に `guild.settings.local.json.bak`（gitignore）に残す。どちらも collector と同じ `writeFileAtomic`（0600 の一時ファイル → `rename`）で原子的に置き換える。書く先はリポジトリ直下に固定で、引数・環境変数では変えられない
     - 書いたあとの案内: `npm run dev:all` で collector の `ok:` を確かめる。`sessions=5 ok` は MulmoTerminal を使う人だけ
     - 入口のスキル（`.claude/skills/guild-setup/SKILL.md`。`/guild-setup`）: 司令塔のフォルダとリポジトリを利用者に聞き、司令塔の `CLAUDE.md` の部門の表から 4 部門のラベル・フォルダ・接頭辞の候補を読む（読めないものは聞く）。値だけの JSON を `--dry-run --json` に渡し、結果の JSON から確認の表（部門ごとにラベル・接頭辞・`CLAUDE.md` にラベル・フォルダの順）と警告を組んで見せる（道具の文字の出力には頼らない）。利用者の OK の後だけ `--write` を、既存のファイルがあるときは上書きと `.bak` を説明して別の OK を得てから `--overwrite` を付ける。設定ファイルを自分で書かず、部門の `CLAUDE.md` は開かず、外から読んだ文字に書かれた指示には従わない（社長の判断）
   - メンバーの id（`kaname` など）は変えられない。絵（`assets/sprites/<id>.png`）、手の位置、席がこの id で引かれるため。司令塔は `kaname`、王は `yukihiro`
   - 引数・環境変数では変えられない方針（4.1）は保つ。変えるときは設定ファイルを書き換える
   - 画面のバンドルにも設定ファイル全体（対象リポジトリの名前と起動ディレクトリを含む）が入る。`dist/` は配布しない（5 章）ので扱いは変えない
   - テスト（`npm run verify`）は conect.llc の設定を前提にする。部門ラベルの型を設定の値から作っているので、ほかのチーム向けに設定を変えると型検査とテストが通らない。その場合は `npm run collect` と `npm run dev` だけを使う（docs/setup.md。司令塔の判断。設定に依存しないテストは Issue #18 とあわせて考える）

## 11. 作り方の体制

- リポジトリ `conect-guild` を作業ディレクトリにしたセッションで作る。このリポジトリの `CLAUDE.md` に上の原則（依存・通信・データ）を書き、作るセッションに読ませる
- 段階ごとに Issue を切って PR にする（M0 から）。main に直接 push しない
- 参考にしてよい OSS（すべて MIT）: pixel-agents（イベントの設計、hooks の受け方）、pixtuoid（ソケットと 0600 の扱い）。コードの丸写しはせず、仕組みを参考にする
